# 项目启动清单、工作卡与验收检查

本文件包含两种第三环记录。只有一项决策结论且无多阶段执行、多个成果或关键依赖时，使用轻量决策行动记录；其他项目在正式执行前集中呈现前三环成果，形成《项目启动清单》及配套《项目推进骨架图》供常浩审核。确认后的记录继续承接执行和验收，保留版本或确认位置。AI 维护；复用已有文档和材料，可调整字段和展示形式，但启动所需内容应完整可读，不让用户自行拼接聊天记录或附件。首轮问挖尚未界定问题时不提前填写规划记录；已有项目复用已确认内容，只补真实缺口。

## 轻量单决策分支

只有一项高影响决策结论，且没有多阶段执行、多个成果或关键依赖时，不使用下方完整启动清单、骨架图和规划包预审。第三环在当前任务中保留一份《决策行动记录》：问题共识基线版本、决策命题、推荐结论与依据、关键假设／最强反证、必要后续动作、改变结论的条件、验收方式和当前证据。完成后跳过第四环，直接按本文件“验收检查”核对实际决策结论；不执行骨架图专项检查。规划确认与最终审核合并。若出现多个成果、阶段、条件分支或持续执行，转为下方完整规划分支。

完整需求应保留已确认的目标、规则、边界、约束和取舍，不能压缩成一句目标。上表“完成后补”的证据字段在启动时可留待执行，其余内容按适用性填写；无相关约束可明确说明，有未知则注明影响与处理办法，不虚构期限、资源承诺或验证结果。效果验证仅在已确认范围内安排，不能由模板新增业务试验。

全项目列全已知成果任务，当前一轮细化操作；条件任务也需工作说明、交付物、完成条件、进入条件与决策时机。调查或研究任务以有证据的判断及边界作为成果，不预先要求某个结论。交付物可以是现有文档的部分，避免把文件数量当成任务质量。表格过宽时可将复杂任务展开为短卡片，仍保留相同信息。

任务必须双向可追溯：每个 `R` 都有任务和产物承接；每个任务都能回指 `R/C`，或明确标为支撑任务、验证样本并给出父需求。`E/Q/A` 未升级前不能直接生成必交付任务。一个任务声称包含多个独立子能力时，每项子能力都要有相应完成条件，不能用一个样本替代其余能力。

## 规划包预审

提交规划确认前，先做以下确定性集合检查；结果不为空就修复，不能用人工主观判断跳过：

```text
未承接需求 = 已确认必须需求 ID - 被任务承接的需求 ID = ∅
无来源任务 = 任务 ID - 有需求／约束／支撑依据的任务 ID = ∅
缺失图节点 = 路线成果任务 ID - 总览及细图节点 ID = ∅
无任务图节点 = 图中执行节点 ID - 任务／门槛 ID = ∅
```

再使用 `advanced-evaluation` 做语义预审，输入包含用户原始表达、最新纠正、已确认基线、当前产物契约、工作卡和全部骨架图；复杂项目在条件允许时优先使用与作者生成过程隔离的审查上下文，不向审查者只提供作者摘要、自评或字段同步结果。独立上下文不可用时，在当前任务中直接从原始材料逐项取证并标明限制，不能虚称独立或跳过语义检查。检查至少覆盖：

- 需求类型和范围是否正确，示例、探索问题和 AI 建议是否被误升格；
- 本轮交付与长期愿景／未来路线是否分开，未来节点是否被误标为当前已激活任务，规划确认是否被误当成扩大执行或写入授权；
- 每项已激活任务的授权是否形成于执行前，记录的对象与当时实际展示范围一致；是否存在执行后改写旧记录、把后继动作倒写成此前已授权；
- 产物对象与目标粒度是否符合契约；
- 要求、任务、成果与图节点能否双向追溯；
- 任务完成条件能否证明其承诺的每项能力；
- 图与任务对开始、联调、验收、用户决定和失败回退的语义是否一致；
- 主流程是否优先跑通，非阻塞边缘项是否有明确回收位置。
- 被纠正或推翻的旧表述是否仍残留在当前有效且被消费的正文、图、任务、验收或机器可读索引中，多版本项目是否有唯一有效版本；已失效历史版本可以保留原貌，但不得再被当前入口引用。

致命或重要问题修复并重验后才可提交用户做原有规划确认。字段逐字一致、跨文件同步成功、图形美观或作者自评都不证明规划语义正确；存在承重路线假设时再调用 `strategy-red-team`。

## 提交前核对与后续维护

- 当前目标与需求能够回指已确认的问题共识基线或后续有效变更；用户原意、事实、AI 推断与待验证事项没有混写。
- 顶部路由状态与当前工作卡、最新版骨架图及可核查成果一致；当前项目交付、已激活任务和允许的动作／写入范围仍符合问题基线与最新授权；无依据的状态标为待核实，不能把状态行当作完成证据。
- 每项有效需求能找到承接任务和最终成果；每项任务能回指需求、约束或明确的支撑依据；示例、探索问题和 AI 建议没有未经确认升级为范围。
- 已知成果任务覆盖当前项目范围，工作说明、交付物与完成条件分别清楚；首份校准（适用时）、必要整合及最终验收在安排中可见。
- 优先级和执行次序均有理由，必要前置、并行与条件分支明确，无循环依赖；受阻任务不列作立即启动。
- 主流程有完整输入到交付的路径和跑通依据；非阻塞边缘问题有后续集中处理安排，必要前置和核心质量要求仍有保障。
- 项目推进骨架图已实际生成且可打开；产物契约明确它不是产品结构图或一次任务运行流程图。它基于已确认的问题共识基线，主线、阶段门槛、关键分支、回退和验收节点与清单一致，“总览＋细图”覆盖全部路线成果任务，每个执行节点能回指任务和交付物，依赖边类型一致，本轮已激活节点与未来路线清楚区分，阶段验证、参考样本、共享底座或子系统没有取代父项目主线。常浩已看到并在同一规划节点确认。
- 资料、资源、用户配合和未决事项有处理办法；清单足以支持当前启动决定，不能以遗漏的关键选择作默认前提。

问题共识基线的语义确认只回答“理解是否准确”；本项核对服务于既有规划集中确认，回答“怎样推进”，不重复询问同义需求，也不增加其他审批。只有清单和当前骨架图都被规划确认覆盖时才直接承接；记录不完整由 AI 补齐，不将补记录当作重新批准全部项目的理由。规划确认只确认路线，不自动解除只读、暂不开发或不改真实系统等既有边界，也不自动激活图中的未来路线。仅获准蓝图、审查或验证时保留后续条件分支；重大变化只提交受影响的选择，并在确认前把候选路线与当前已确认版本分开。确认后维护一份当前有效工作卡，并保留最新版骨架图。任务状态变化只更新工作卡；主流程、阶段顺序、关键分支、回退或验收节点变化时，确认后同步更新当前骨架图和版本关系。后续获得更大授权时追加新的来源、时间和适用范围；不得覆盖旧记录或用执行结果反推用户此前同意了更大范围。

事实与假设明确区分即可，不为每句话编号；复杂、多项或容易误解的输入必须给需求和任务稳定标识，简单项目可保持轻量。位置可以是对话轮次、文档章节、文件或已授权读取的外部对象。

状态用业务可理解的“待做／进行中／待校准／已完成／暂缓／受阻／已失效”，按实际需要选用。成果位置可访问并且内容满足完成依据，才标已完成；若只找到完成标记而无法核对成果，写“记录称完成，成果待核实”。暂缓项按总路由的主流程优先规则维护，在总验收前核对处置及对有效要求的影响。

## 验收检查

总验收读取已确认的问题共识基线、后续有效变更及实际成果；完整规划分支另读启动清单，轻量单决策分支另读决策行动记录。只验收本轮交付和已激活任务；未来路线是否已完整、清楚地规划可以是当前成果要求，但未来节点本身不因未执行而判为未完成。执行常浩既有六项审查：

验收方法使用 `advanced-evaluation` 的业务适配：先查每项要求的来源和通过条件，再记录证据，最后判断满足／部分满足／未满足／无法验证。单列关键缺失与无法验证项的影响，不能用总分抵消；早期未留基线时明确本次回溯核查的依据及覆盖限制。

1. **逻辑断点**：结论是否有足够依据，推理是否跳步？
2. **隐含假设**：决定性前提是否声明，已验证与待验证是否分开？
3. **完整性缺口**：每条有效要求是否覆盖，关键问题是否回答，范围是否遗漏？
4. **可实现性**：动作是否符合现实资源、成本和依赖；约定可执行的成果是否足以使用？
5. **边界条件**：异常、失败和适用范围是否影响结论或使用？
6. **目标偏差**：成果是否解决原问题，分块成果整合后口径、术语与建议是否一致？

完整规划分支另以最新版骨架图复核执行完整性：必经节点是否完成，实际触发的分支是否处理，未触发分支是否有条件依据，回退后旧成果是否失效，最终验收节点是否真正到达。骨架图与有效需求或成果冲突时，以最新确认要求和可核查证据为准，并先修正图，不能用图替代事实。轻量单决策分支不执行本项。

问题标注“致命／重要／建议”，每条带位置、理由和影响。分类以对项目目标或成果使用的影响为依据，不为凑数量制造问题。授权修订时先修重要问题再交付；纯审查时仅标注。最终展示可压缩为已覆盖要求、实际验证、未决限制和用户需判断之处，无须输出完整检查过程。

已交付方案并不自动证明业务效果。真实试点尚未开展时明确范围；是否接受由常浩决定，不自行新增必需试用人或长期追踪。用户接受已知限制时记录接受的具体限制，验收状态可以通过，证据状态仍保留未验证。
