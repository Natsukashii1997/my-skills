# 深度框架：从证据推到决定

标准提示词交代“这一步做什么、给谁看”。这份说明“做到多深、怎么做深”。三步都用；每一步的论证逻辑和可选的分析手法，在各自 reference 的“论证逻辑”和“深度动作库”里；三步共用的数据本体论方法见 [data-ontology.md](data-ontology.md)，怎么把问题问到底见 [deep-dig.md](deep-dig.md)，页面怎么做到网页质感见 [presentation.md](presentation.md)。

先记住一条：**产出的厚度来自证据的密度，不来自篇幅，也不来自章节数。** 不为凑篇幅加章节，也不为省篇幅砍证据。

## 0. 先定每一步给谁看

三步的读者不同，读者决定了报告的立意、语言和论证顺序。动手前先对照这张表，确认这一步写给谁、他要拿什么走。

| 步骤 | 主要读者 | 读者要从报告里拿到什么 | 语言 | 定位立意从哪来 |
|---|---|---|---|---|
| 一 · 访谈提纲 | 业务团队：一线受访者和业务负责人；访谈者 | 受访者看懂要做成什么样、对自己有什么用，愿意配合、把真实的工作讲出来；访谈者知道为什么这样问、问到什么程度才够 | 业务自己的话和界面画面，不用技术术语 | 理想图景（要做成什么样、能帮一线做什么、为什么这样建），加上这次访谈要弄清的事。这一步是展示和调研：先说明，再启动；第二步的质量取决于这一步挖得多深 |
| 二 · 技术方案 | 产品和技术：技术（架构师、开发）建表、写规则、开接口；产品把需求落成视图、排优先级和分期 | 这是一套什么系统、为什么这样设计、数据从哪来；技术拿到就能建表、写规则、开接口，产品拿到就能出原型、排分期 | 技术术语和专业图：ER 图、状态机、事件表、规则配置、接口。用数据本体论组织，见 [data-ontology.md](data-ontology.md) | 这套东西整体是什么（路觅案例里是“销售工作台和侧边栏的整体设计”），加上设计思想。这一步是需求反馈和路径分析 |
| 三 · 执行规范 | 产品和技术：产品设计分角色的流程和界面，技术落实留痕和检查指标 | 每类人处理哪些业务单元、每个动作留下什么数据、怎么检查；和第二步读者相同，第二步看系统整体怎么建，这一步看每类人怎么用；哪些缺口要交回第二步 | 产品语言加本体术语：角色、动作、规则、指标、写回字段 | 方案怎么落到每类人，加上这次要出规范的原因。这一步是梳理补充 |

**定位立意和发现是两回事。**

- 定位立意回答“这是什么、为什么这样设计、依据什么”，由读者、这一步的目的和本案的设计对象决定，写在首页。设计对象是整套系统，立意就覆盖整套系统；开篇引语要服务整体立意，不能拿一个小点撑起全篇。
- 发现回答“材料里看到了什么”，是论证的证据。它填进分析那一段，用来推出具体的设计决定，比如某个东西要成为独立对象、某条规则的阈值定多少。发现不当立意，也不给章节命名。
- 判别办法：只读首页，读者能说出这是一套什么东西、设计思路是什么、数据从哪来吗？如果首页讲的只是一个数据发现，就是把立意窄化了。

**结构按读者的论证逻辑排。** 每一步的 reference 都有一节“论证逻辑”，写明给这类读者讲清一件事要经过哪几部分、按什么因果顺序、每部分起什么作用。章节名、要不要合并或拆分、加不加本案特有的专题，都可以按场景改；顺序和每部分的作用不能丢。

## 1. 八步

执行时按顺序走。前五步的产物多数是中间材料，不一定进报告，但必须真的做过；报告里的每个结论都应该能追回到其中某一步。

| 步 | 做什么 | 留下什么 | 什么时候算完 |
|---|---|---|---|
| 1 盘点材料 | 列出全部材料，逐个打开、核对完整 | 材料盘点表 | 每份材料都能打开、是完整的，或已写明缺什么、为什么不影响结论 |
| 2 列决定 | 写出读者看完要做的决定 | 决定清单（3–8 条） | 每条都写成“谁要决定什么” |
| 3 提问题 | 把每个决定拆成要先回答的问题，标出答案从哪来 | 问题清单 | 每个问题都标了来源：访谈、数据、用户拍板或外部事实 |
| 4 取证 | 用材料回答问题，访谈和数据互相核对 | 证据表、分析脚本 | 每个问题都有答案，或写明答不了的原因 |
| 5 找关键发现 | 从证据里挑出最改变设计的几个发现 | 3–5 个发现，每个写清推出了哪个设计决定 | 拿掉任何一个发现，对应的设计决定会跟着变 |
| 6 排结构 | 按这一步读者的论证逻辑排骨架，再用本案的决定、问题和发现填进去 | 章节表（每章在论证里起什么作用、回答什么） | 论证逻辑的每一部分都有着落；每章对应一个决定或问题，没有空章，也没有重复 |
| 7 写到能用 | 按这一步的“能用”标准写 | 报告 | 读者拿到就能做下一件事，不用再问“具体是什么” |
| 8 自检和独立审查 | 先过自检题，再请独立审查 | 检查结果 | 审查意见已改，或已写明为什么不改 |

### 1 盘点材料

- 列一张表：材料名、类型（访谈纪要、逐字稿、聊天导出、截图、方案文档）、原始还是二手、是否完整、能否打开、覆盖哪条业务线或哪类人。
- 逐个核对：
  - 压缩包解压后，对照包内文件数和解出的文件数；
  - 导出数据算清总条数和时间范围；
  - 文档逐个打开，打不开的请用户开权限，不绕过，也不跳过。
- 同一场访谈既有 AI 纪要又有逐字稿时，读逐字稿，纪要只当目录用。纪要会丢掉原话、数字和语气。
- 用户口述和原文冲突时，以原文为准，并告诉用户。
- 做对比测试或复现时，输入必须和对照组一致：数据条数、访谈份数、需求材料都要对齐。没对齐就先停下来补齐。
- 盘点表最后写进报告的口径与局限。

### 2 列决定

读者看完报告要拍板什么，就写什么。

- 技术方案：技术要决定先建哪几张表、接哪几个系统、规则怎么配；产品要决定需求落成哪些视图、哪些能力这一期不做、每期怎么验收。
- 访谈提纲：访谈者要决定这一场重点问什么、每段花多少时间；受访者要能判断这件事跟自己有什么关系。
- 执行规范：产品要决定每类人的流程、动作和检查口径怎么设计，哪些缺口交回第二步；技术要确认每个动作的留痕在本体里有字段、检查指标算得出来。

决定清单决定了这份产出的重心。写不出决定，说明还没弄清读者是谁，回到第 0 节。

### 3 提问题

把每个决定拆成要先回答的问题，标出答案从哪来：

- 访谈能回答的，标出是哪一场；
- 数据能回答的，写出怎么算（分子、分母、时间窗口、剔除什么）；
- 只有用户能拍板的，记进待确认清单；
- 需要外部事实的，比如接口权限，标“待验证”。

先写问题，再看数据。反过来做，就会变成“数据里有什么就报什么数字”。

问题清单里必须有差异类问题：按 [deep-dig.md](deep-dig.md) 第 2 节把角色、熟练度、业务线、服务对象、情境、结果、现有工具逐个过一遍，每个维度写出“这里可能有什么不同”和怎么验证。每个业务单元按 deep-dig 第 3 节追到六层。

### 4 取证

- **访谈和数据互相核对。** 访谈里的量级、频率、先后顺序，用数据核一遍。不一致时两边都写，并解释差在哪，比如“访谈说的是深度跟进的人数，数据里是全部有发言的客户”。
- **数字带口径**：样本、时间窗口、分子分母、剔除了什么。样本不是全量，就不给看起来像全量的比例。
- **原话带出处**：哪一场、什么时间点。推断和事实分开写，推断要标出来。引号里的原话，写进报告前回逐字稿原文核对一遍；子代理带回的摘录常常是改写，不能直接加引号。
- **量结果，不量代理。** 要回答“做没做成”，就量做成的痕迹。路觅模拟测试里，用“承诺后客户有没有追问”代替“承诺有没有兑现”，得出“承诺不值得单列”，和兑现数据的结论正好相反。
- **差异按维度分组算。** 问题清单里的每个差异维度，能从数据分组算的都算出来，比出真假再下结论。
- **分析写成脚本并保存**，能复跑，结果汇总成一份统计文件，报告里的数字都从这里来。
- **大材料用脚本或子代理读**，只把结论和关键原话带回主线，不把原文整份塞进上下文。

### 5 找关键发现

从证据里挑出 3–5 个最改变设计的发现，每个写清它推出了哪个设计决定。好的发现通常出在这几处：

- 访谈和数据冲突的地方；
- 量最大或断点最集中的地方；
- 和直觉相反的地方；
- 一线自己在手工补的地方（手抄表格、自建工具），这往往说明系统缺了什么。

检验办法：拿掉这个发现，对应的设计决定会不会变？不变的，就不是关键发现。

发现是论证的证据，不是报告的立意（见第 0 节）。它们填进论证逻辑里分析的那一段，比如技术方案的“数据从哪来”前后，或者放在它推出的设计决定旁边作依据。不要用发现给章节命名，也不要把某一个发现写成首页的定位。

### 6 排结构

先按这一步 reference 的“论证逻辑”排出骨架，再用四样东西去填：读者要做的决定、关键发现、提示词要求必答的内容、本案特有的诉求。

- 首页按第 0 节写定位立意：这是什么、设计思路、依据什么。
- 论证逻辑的每一部分都要有着落。本案确实用不上的部分，写明为什么不需要，不悄悄删掉。
- 每章写清它在论证里起什么作用、回答哪个决定或问题。两章回答同一个问题就合并。
- 章节名用这个业务自己的话，可以改名、合并或拆分；顺序和每部分的作用不能丢。
- 本案特有、又足够重的差异（比如新老销售的工作流不同，后续要各做一套流程），单独成一个专题章，放在论证逻辑指定的位置。
- 有多条业务线或多类人群时，先用证据验证差异是不是真的，再决定差异落在哪一层：字段、规则、页面、指标，还是整套分开。多数差异落在字段和规则层，共用的部分做深，不要整页复制两份。
- 范例的章节只用来查漏：对照看是否漏掉了某类必答内容。论证顺序按 reference 的“论证逻辑”，不按范例的章节；章节名和多少章从本案定，也不照范例。

### 7 写到能用

每一步的“能用”标准见对应 reference 的质量特征。通用的一条：读者拿到就能做下一件事。技术能开表，产品能出原型、排流程，访谈者能开口。

### 8 自检和独立审查

1. 逐条过第 3 节的自检题。
2. **机械核对一致性。** 不靠印象打勾，写脚本或逐项列表核对：
   - 列出报告里出现的全部对象、字段、事件编号、待办编号、状态名；
   - 每个写回字段、规则里用到的字段，都能在字段表里找到；
   - 每类待办都指向一个事件和一条规则，编号前后一致；
   - 同一个状态在状态机、事件表、界面里叫同一个名字；
   - 引号里的原话在逐字稿里找得到；
   - “都”“普遍”“一致认为”“几场都提到”这类概括，逐场列出出处，数得上才这么写；
   - 页面上的每个数字，都能在同一份统计文件里找到同一个值；中间稿和页面对不上时，以统计文件为准，两处都改；
   - 原型和演示里的示例数据，代入它所展示的规则算一遍：触发条件确实成立，时间先后对得上，完成方式和规则一致。
   路觅模拟测试里，自检全部打勾，独立审查却查出 15 处前后对不上，就是少了这一步。新用户盲测里，“五场都排第一”实际只有两场、中间稿和页面的同一个比例不一样、原型里“客户未回复”的提醒挂在销售已经回过的会话上，也都是独立审查才查出来的，所以补了后三项。
3. **截图检查呈现**，按 [presentation.md](presentation.md) 第 3 节。
4. 再起一个独立的 agent 审查。给它这几样：报告、用户需求和原话、材料盘点表、这份框架、deep-dig、presentation、对应步骤的质量特征和检查项，不给你的思路和中间结论。请它找出最浅的三处、缺证据的三处、漏掉的差异维度、首页是否窄化、结构哪里偏离了论证逻辑、呈现哪里干巴巴。
5. 按审查意见改一轮；不改的，写明理由。改完核对改动本身对不对（改动最容易引入新的不一致）；改动大的，再审一轮。

## 2. 质量特征：浅和深的差别

表里的例子来自路觅销售案例，只用来说明浅和深差在哪；换了业务，要用这个业务自己的例子来判断。

| 特征 | 浅 | 深 |
|---|---|---|
| 出处 | “销售普遍反映……” | “国课座谈 00:51 原话：……”；“15 天 105,032 条消息中，X / Y（口径：……）” |
| 访谈 × 数据 | 只引用访谈 | “访谈说日均约 10 个客户；数据里每天有发言的客户中位数是 55–78 个。差别在于访谈只算深度跟进的人” |
| 立意与结构 | 首页是一个数据发现或一张功能清单；章节按零散发现命名 | 首页讲清整体是什么、设计思想、数据从哪来；结构按读者的论证顺序，发现在分析段里推出设计决定 |
| 语言 | 给技术看的报告用业务口语和比喻 | 给技术看用 ER 图、状态机、事件表、规则配置、接口；给业务看用他们熟悉的界面和说法 |
| 粒度 | “建一张事件表” | 写出字段和约束：事件只追加、必须带主体和发生时间、完成必须留凭证，避免重复生成 |
| 闭环与边界 | “推送提醒” | 一直走到写回；写明夜间消息、群里谁是客户、重复识别、误报怎么撤销 |
| 差异 | “两条线结构不同，所以分两版”；只比了用户提到的那一种差异 | 角色、熟练度、业务线、服务对象、情境逐个过；用数据比出哪些是真的，说明落在哪一层、哪些照样共用；不存在的写明依据 |
| 指标 | 用好量的代理指标回答问题（“客户有没有追问”） | 直接量结果（“承诺有没有兑现”），代理指标只作补充 |
| 呈现 | 灰底加一张接一张的表格，原型是线框 | 首屏画出全貌，有留白和节奏，原型高保真，需求逐项有图，核心链路可播放 |
| 验收 | “提升效率” | 用历史数据回放的指标和阈值，比如抽取的召回率和准确率 |
| 推进 | “先给哪几位销售试用” | 能力评级（能力 × 涉及对象 × 本期是否必需 × 数据代价 × 能否用现有数据验收 × 主要风险）、分期路线和每期验收、上线前必须补的数据 |
| 口径 | 数字没有来源 | 每个数字都能用保存的脚本复现，局限写在旁边 |

## 3. 自检题

1. 材料盘点表里，每份材料都能打开、是完整的吗？逐字稿读了吗？
2. 写得出读者要做的决定吗？每章对应哪一个？
3. 关键结论里，有原话或带口径数字作出处的占多少？没出处的是否都标了“推断”？
4. 访谈里的量级说法，有没有用数据核过？不一致的地方写了吗？
5. 只读首页，读者能说出这是什么、设计思路是什么、数据从哪来吗？立意覆盖了整体，还是只讲了一个发现？
6. 结构是按这一步读者的论证逻辑排的吗？每一部分都有着落吗？章节名是本案的话，还是照着范例或零散发现起的？
7. 每个关键发现推出了哪个设计决定？拿掉它，这个决定会变吗？
8. 读者拿到能直接做下一件事吗？还有哪处一定会被追问“具体是什么”？推进部分对读者有用吗（技术方案里，开发能拿它排期和验收吗）？
9. 每条链都走到写回、走到检查了吗？边界和反例写了吗？
10. 多业务线或多人群的差异，是验证过的吗？落在了哪一层？
11. 有没有为了省篇幅砍掉证据，或者为了凑篇幅加了空章？
12. deep-dig 的差异维度每一个都有结论吗（是真的、落在哪层，或者不存在、为什么）？
13. 一致性的机械核对做了吗？对不上的都改了吗？
14. 页面过了 presentation.md 的底线吗？用户给的每项功能需求都画出来了吗？

## 4. 反模式

| 反模式 | 实际发生过的例子 | 怎么避免 |
|---|---|---|
| 照搬范例的章节 | 重做技术方案时，准备逐章复刻范例的 13 章 | 结构按第 6 步排，范例只用来查漏 |
| 首页窄化 | 技术方案首页写“一套事件底座，挂在试听和课号上”，开篇引语用一位销售的一句话，读者看不出这是销售工作台和侧边栏的整体设计 | 首页按第 0 节写定位立意：整体是什么、设计思想、数据从哪来；引语服务整体立意 |
| 用发现给章节命名 | 按十几个零散的数据发现各起一章，因果顺序被打碎，读者跟不上“为什么要这么做” | 先按论证逻辑排骨架，发现填进分析段，在它推出的设计决定旁边作依据 |
| 把发现当立意 | 深度框架旧版第 5、6 步把“主线发现”当成报告的立意和结构来源，上面两条都是从这里来的 | 立意由读者和这一步的目的定，发现只当论证的证据 |
| 推进写成“先给谁用” | 技术方案的推进部分写“先给哪几位销售试用”，开发拿到不知道先建什么、做到什么算完 | 写能力评级、分期路线和每期验收、上线前必须补的数据 |
| 给技术看却不用术语 | 技术方案通篇业务口语，没有 ER 图、状态机和事件表，架构师对不上 | 按数据本体论组织，用专业图和术语，见 [data-ontology.md](data-ontology.md) |
| 数据当装饰 | 10 万条聊天只算了几个关键词比例，用来给已写好的结论配数字 | 先写问题清单，用数据回答问题 |
| 只读 AI 纪要 | 逐字稿链接就在纪要里，没有打开 | 盘点时纪要和逐字稿都列上，读逐字稿 |
| 不核对材料完整性 | 解压时报了错，825 个文件只解出 625 个，没有发现 | 解压后对照文件数，导出后对照条数 |
| 用建议值盖住缺失的材料 | 没问会议纪要、需求文档，直接写“没有会议复盘” | 盘点表里列出该有而没有的材料，先问用户 |
| 为省篇幅压缩 | 主动把统计输出和正文压短 | 用脚本和子代理保护上下文，不靠砍内容 |
| 拿视觉打磨充当质量 | 动画演示做得很细，分析却停在表面 | 先过自检题，再做视觉 |
| 差异落错层 | 两条业务线各写一整套页面，每套都变薄 | 先验证差异，再决定落在哪一层 |
| 检查只问有没有 | 浅版本也能在“有对象关系图”“写了事件表”上全部打勾 | 用第 2 节的浅深对照来检查 |
| 只挖用户提到的差异 | 用户说了“两条线不同”，就只比两条线；访谈里有三位新人，新老销售的差异没有验证 | 按 deep-dig 第 2 节把差异维度逐个过 |
| 代理指标反转结论 | 用“承诺后客户有没有追问”判断承诺不重要，而兑现数据显示四到五成承诺 72 小时无完成痕迹 | 量结果，不量代理 |
| 自行推翻用户的结构要求 | 用户说“两条线要分开做”，报告直接改成“一套系统两份配置”，只标了待确认 | 证据和用户原话相反时，摆出证据，停下来问 |
| 需求没画出来 | 用户第一项功能需求“试听课表日历”只在图注里带过 | 做“需求 → 视图”对照表，每项都有原型 |
| 页面干巴巴 | 内容完整，但页面是灰底加表格，原型只有线框，被评“没有设计感、美感、空间感” | 按 presentation.md 做到网页质感 |
| 自检凭印象打勾 | 自检全部通过，独立审查查出 15 处前后不一致 | 第 8 步的机械核对 |

## 5. 怎么用范例

各步 reference 链接的路觅原页是质量参照，不是模板。读范例时，看它怎样从一句原话或一个数字推到一个设计决定；不要看它有几章、章节叫什么。

换场景时会变的：读者要做的决定、问题清单、选用哪些分析手法、关键发现、章节名和章数。不会变的：每一步的读者和论证顺序、八步、质量特征、自检题。

## 6. 深度附言

把填好的提示词发给别的 AI 时，八步和论证逻辑不会跟着过去。在附件最后加一个 `<深度要求>` 标签，放下面这段；再加一个 `<论证逻辑>` 标签，放这一步 reference 里“论证逻辑”那张表。两个标签都不改提示词正文，作用和 `<背景>` 标签一样：

```
<深度要求>
1. 动手前逐个打开全部材料，核对是否完整；有逐字稿读逐字稿；打不开或不完整的，先告诉我，不要跳过。
2. 先写出读者看完要做的决定，再把每个决定拆成要回答的问题，标出答案来自访谈、数据还是需要我拍板。
3. 过程数据用来回答这些问题：核对访谈里的量级说法、量化问题、找出访谈没说到的断点。数字写清口径。
4. 首页先交代这是什么、设计思路是什么、数据从哪来；立意覆盖整体，不拿某一个发现当立意。
5. 结构按 <论证逻辑> 里的顺序排，每一部分的作用都要有；章节名用这次业务自己的话，可以改名、合并或拆分。
6. 从证据里找出最改变设计的 3–5 个发现，填进分析部分，各自推出一个设计决定；不用发现给章节命名。
7. 写到读者能直接开工的粒度，写清边界和反例；能用历史数据回放的验收，写出指标和阈值。
8. 每个结论带出处（原话或带口径的数字），推断单独标出；引号里的原话回原文核对过；局限写清楚。
9. 把差异问到底：不同角色、新人和老手、不同业务线、不同服务对象、不同情境，逐个想过、用材料验证过；只能由我拍板的，先问我。我明确提过的要求和证据相反时，先问我，不要自己改。
10. 量结果，不量代理：要判断一件事做没做成，就量做成的痕迹。
11. 页面要有网页的质感：首屏画出全貌，有留白和节奏，原型照真实界面高保真还原，我给的每项功能需求都画出来，核心流程能播放演示；能生图就用生图。
12. 交付前机械核对一遍：每个写回字段、事件编号、状态名前后一致，都能在字段表和事件表里找到。
</深度要求>
```
