# 第二步 · 技术方案：把业务语言翻译成技术语言

翻译方向是业务 → 技术。访谈拿回了大量业务原话，研发却无从下手；这一步要把“业务说的事”对到哪条数据、哪个事件、哪个页面，让方案能直接开工。

- **对象**：管理层和技术团队。
- **输入**：访谈报告（主要依据）+ 过程数据材料 + 会议复盘。
- **产出**：一份技术方案，核心是数据本体和每个业务单元从取数到写回的链路。
- **交给下一步**：已定方案，也就是业务单元怎么流转、数据怎么回流、业务流怎么打通。

## 先行判断

1. **产出的对象从业务换成了管理层和技术团队。** 业务说的“该联系了”“答应了家长的事”，技术接不住，要翻译。
2. **真正的难点是抽象。** 技术功能和业务是什么关系不清楚；要做的东西如果还没开发出来，就更抽象。
3. **业务最终看到的都是一个个业务单元**（路觅案例里是一张张待办卡）。所以翻译的抓手是：每个业务单元从哪来、到哪去。

用户的局面和这三条不一样时，按 SKILL.md 第 4 节 ① 处理。常见的差异：对象不是内部技术团队，比如外包团队（填进“技术团队”槽位）；团队还没有现成系统（删掉“已有系统”槽位）；技术实现条件还没定（写进“技术基础”和“更抽象的原因”槽位，提示词里已经要求标“待验证”）；业务单元还没定清楚（先从访谈报告和过程数据里找出一线要处理的事项，作为建议值填进去；材料不够，或者不同的定义会让方案走向不同时，再请用户确认）。

## 要问用户的

SKILL.md 第 2 节第一轮问完后，从下面挑还没有答案的问，问法照第 2 节：用业务的话、给选项或示例、带推荐答案。“必答”的问了还是没有，按 SKILL.md 第 1 节停下。

| # | 问题 | 选项、示例或推荐 | 不知道时 | 用在哪 |
|---|---|---|---|---|
| 1 | 访谈做完了吧？把访谈转写、纪要或整理好的报告贴上来（原文）。 | 有几份就贴几份 | 必答；没有就建议先回第一步 | `访谈报告` |
| 2 | 一线平时工作会留下哪些记录？聊天记录、工单、表格、系统日志……能导出哪些、大概多长时间的？ | 例：“企微会话归档能导出，Excel 登记表有近三个月” | 先按访谈做，数据来源都标“待验证” | `过程数据`、`数据来源`、`过程数据材料` |
| 3 | 这份方案给谁看？谁来开发：内部技术、外包，还是还没定？ | 推荐：给管理层和技术团队看 | 按“管理层和技术团队、开发方待定” | `汇报对象`、`技术团队` |
| 4 | 做开发的人现在会用什么工具？有没有现成的系统？ | 例：“外包会用飞书多维表格和简单的 API；没有报修系统” | 按“技术路线还没定”，写进技术基础 | `技术基础`、`已有系统`、`更抽象的原因` |
| 5 | 最后希望一线在哪里用到：手机、电脑客户端、群机器人、后台看板……？ | 不确定就让你根据技术基础建议 | 你给建议，标“待验证” | `技术落点` |
| 6 | 有没有会议纪要或上一轮讨论的结论？直接贴原文。 | 没有就说没有 | `<会议复盘>` 里写“没有会议复盘” | `会议复盘` |

## 设计决策

| 判断 | 所以提示词要 | 对应段落 |
|---|---|---|
| 这份报告要对接下一步开发 | 开头先说清任务：把反馈翻译成技术方案，对应到开发工作 | 任务 |
| 知道对象会什么，才知道用什么话讲 | 交代谁来实现、他们现在的技术基础、现有系统基于什么搭建，再用他们熟悉的概念来讲 | 汇报对象 |
| 抽象是最大障碍 | 直接写出抽象在哪：功能与业务的关系、需求怎么落成功能页面 | 难点 |
| 需求要落到数据上 | 抓两条线：业务流对数据节点，数据流对产生业务单元的数据或状态变化；先画图谱再分析 | 两条线 |
| 研发要能开工 | 回答数据本体、每个业务单元从取数到写回本体的完整链路，以及事件表怎么建 | 两条线 |
| 架构师要能直接对上，推测不能当事实 | 写明要落到哪几端，多用对象关系图和流程图；能确认的照实写，要验证的标“待验证” | 落点与形式 |

## 骨架公式

**任务 × 汇报对象 × 难点 × 两条线 × 落点 → 可开工的方案**

缺了“两条线”，方案会变成功能清单；缺了“落点”，架构师对不上；缺了“写回”，业务单元没有闭环。

## 标准提示词（v8.1）

本步专属槽位：

- `汇报对象`、`技术团队`、`技术基础`：照实写给谁看、谁来做、他们现在会什么。技术基础可以写已经会用的工具和了解的概念，也可以写还没定工具或技术路线、对相关概念不熟。
- `已有系统`：没有现成系统时删掉。
- `更抽象的原因`：没有额外原因时删掉。已经写进 `技术基础` 的（比如技术路线还没定），这里不再重复。
- `数据来源`：列出可能取数的系统，帮 AI 把链路落到具体来源上。
- `技术落点`：方案最终要落到哪几端。技术还没定时，写目前倾向的几端，报告里标“待验证”。
- `访谈报告`、`过程数据材料`、`会议复盘`：附原文。访谈报告是主要依据，访谈纪要或转写也放在这里；没有任何访谈材料时，回到 SKILL.md 第 3 节。还没有过程数据时，`<过程数据>` 里写“暂无过程数据”，并在报告的局限里写明。

```
我们已经和{{一线角色，例：销售}}做完访谈，访谈报告附在后面。现在要把业务人员的反馈翻译成技术语言，写一份技术方案，让大家清楚这些反馈具体对应到下一步开发的哪些工作。

这份报告要给{{汇报对象，例：管理层和技术团队}}看。{{技术团队，例：我们的技术同事和各业务板块的架构师}}{{技术基础，例：已经会用 Hermes 等基础工具，基础概念都了解}}，{{已有系统，没有可删，例：现有的销售看板也是围绕这些技术搭建的，}}所以请用他们熟悉的概念来讲。

难点在于：技术功能和业务之间到底是什么关系，业务提出的需求又该怎么落成具体的功能页面，这件事很抽象。{{更抽象的原因，没有可删，例：加上要做的工作台还没开始开发，就更抽象了。}}

请用全局的视角，抓住两条线来分析。一条是业务流：业务人员谈到的每个场景和事件，背后对应哪个数据节点或哪些关键数据。另一条是数据流：一线要处理的每一个{{业务单元，例：待办}}可能由哪条数据产生，比如人在翻看{{过程数据，例：企微聊天记录}}时会记下的事项，技术侧能由哪类数据或哪种状态变化自动识别出来。请先把这两条线画成一张图谱，再基于图谱展开分析，分析中回答这几件事：

1. 业务背后最关键的对象有哪些，它们之间是什么关系、处在哪个环节、状态怎么变化，也就是数据本体；
2. 每一个{{业务单元}}：数据从哪里取（{{数据来源，例：会话归档、中台、排课系统、日历}}），事件怎么标记，推给谁，对方看到什么内容和上下文，怎样算完成，结果怎么写回本体；
3. 事件表应该怎么建。

最终要让业务的说法能落到{{技术落点，例：客户端、服务端、中台}}上。材料里能确认的数据来源和规则照实写；还需要验证的接口、字段或数据质量，标明“待验证”，不要写成已经具备的能力。表达上多用对象关系图和流程图，方便架构师直接对照。输出一个单页 HTML。

访谈报告是主要依据，过程数据和会议复盘用来补充背景、核对细节。
```

## 深度动作库

这些是做技术方案时可以选用的分析手法，不是固定章节。按这次的问题清单（深度框架第 3 步）挑：哪个手法能回答读者要做的某个决定，就用哪个。这张表是从过去的案例里归纳出来的，不全。问题清单需要、表里又没有的手法，自己设计，写明口径。括号里的例子只是帮助理解，换了业务要换成这个业务自己的东西。

| 手法 | 什么时候用 | 怎么做（口径要点） | 能推出什么 |
|---|---|---|---|
| 量级核对 | 访谈里有“一天几个”“多久一次”这类量级说法 | 用过程数据算同一个量，写清口径（全部触达还是深度处理），和访谈值并排放 | 看板按什么计数；访谈和现实差在哪 |
| 时间形状 | 工作量在时段、星期或时区上分布不均 | 按小时、星期统计进来的量和处理的量；跨时区时换算到对方当地时间 | 什么时候推送、要不要做批量清单、哪些时段不计超时 |
| 状态时长 | 业务单元会在几个状态之间流转（如工单、审批、试听） | 统计每个状态停留多久、在哪一段停得最久、哪一段没有任何记录 | 哪一段是黑箱；超时规则的阈值；首期先打通哪一段 |
| 重复发生 | 同一对象会反复出现（如重复进线、反复催问、多次改期） | 按对象计数第二次及以后的出现，找出触发原因 | 哪些重复可以靠主动告知消掉；待办怎么去重 |
| 渠道与身份结构 | 工作分散在多个渠道、多方会话或多个系统 | 统计各渠道占比；看每个会话里发言的都是什么身份；会话名、单号里编码了哪些信息 | 记录怎么落到具体对象；身份识别的优先级；哪些信息可以直接解析 |
| 断点追踪 | 要找推动一线的抓手 | 找出事情在哪一步最常停下：首次响应、提问得到回答、一线说出的承诺有没有完成痕迹、被反复催促的环节 | 哪类待办最值得先做；规则阈值的依据 |
| 从手工记录反推字段 | 一线在手抄表格、发交接单、自建工具 | 抽出手工记录的结构，统计字段出现频次，对照现有系统缺什么 | 本体字段；哪些可以由系统抽取，哪些要人确认 |
| 噪音剔除 | 过程数据里有群发、模板、机器人、撤回等非真实交互 | 识别跨会话逐字相同的内容，按类型过滤 | 识别事件前先做的清洗；不剔除会误报多少 |
| 沉默与回归 | 要设计回访、激活或流失规则 | 统计对象沉默多久之后还会回来，回来时由什么触发 | 回访靠节点还是靠问候；N 天阈值的依据 |
| 高频动作计数 | 要决定界面上放哪些动作、按什么顺序 | 统计一线反复做的动作的频次和耗时，反复发送的素材有多少 | 动作清单和默认顺序；素材或模板的优先级 |
| 分组差异 | 有多条业务线、多类人群，或用户要求分开做 | 上面各项分组计算，比出真正的差异 | 差异落在字段、规则、页面还是整套分开；哪些照样共用 |
| 现有工具逆向 | 一线自建过工作台、表格或流程 | 拆出它的视图、状态、排序方式和提醒规则 | 界面需求；一线已经接受的状态命名 |

## 质量特征与范例

一份能开工的技术方案通常要体现下面四组质量。路觅案例里，这些质量长成了 13 个章节，但那只是那一次的样子，是那个案例的读者、诉求和数据发现决定的。这次的章节按深度框架第 6 步从本案推导。下表只用来查漏：看有没有漏掉某一类质量，不用来决定写哪些章、叫什么名字。

| 组 | 要体现的质量（与场景无关） | 来自提示词 | 路觅案例里长成的样子（只作参照） |
|---|---|---|---|
| 结论先行 | 管理层不读完全文，也能在开头拿到结论、全貌和最关键的发现；全貌要让人看出信息在什么时候、以什么方式到达一线 | 汇报对象 | 一页结论（十句话）；以一位销售真实的一天为例，标出工作台在哪几个时刻推信息 |
| 数据与本体 | 业务说法对到数据，业务单元追到对象的变化；每个对象写到字段、关系和状态；每类业务单元都能指向一个本体事件 | 两条线 | 六个问题六张表；九个对象的字段表；十二类待办各对应一个事件 |
| 落到能开工 | 需求落到读者能开工的界面或接口，每个界面动作对应哪次写入；数据从产生到写回走得通 | 难点、落点与形式 | 今日视图、月历视图、右侧边栏，加一张回流字段表 |
| 证据、边界与推进 | 差异和优先级有数据依据；先做什么、为什么、做到什么算完都写清；每个数字有口径，局限不藏 | 材料 | 新老销售对比；最需要被管的信息；四期路线和回放验收；口径与局限表 |

每个业务单元都要能走完这条链：**取数 → 标记事件 → 规则判定 → 推给谁 → 展示什么内容和上下文 → 怎么完成并写回本体**。路觅案例里，销售随口一句“稍后回您”，经会话归档取到，被标记为一次承诺事件，超期且客户追问时生成高优先级待办，推给这位客户的归属销售，完成后写回“承诺已兑现”。

路觅原页：《路觅销售工作台 · 整体设计（数据本体 + 侧边栏）》（2026-11-04，13 章，依据 6 份访谈和 105,238 条消息）<https://s3.fmode.cn/user/K0xKEZANOG/lumi/workbench-design/index.html>。读它时，看它怎样从一句原话或一个数字推到一个设计决定，比如从“稍等、我查一下”的兑现率推出“承诺”要成为独立对象；不看它分几章、章节叫什么。原页打不开不影响检查，以上表为准。

## 检查项

材料：

- [ ] 有材料盘点表，每份材料都打开过、核对过完整性（压缩包对文件数，导出数据对条数）。
- [ ] 有逐字稿的访谈读了逐字稿；打不开的已请用户开权限，没有跳过。
- [ ] 该有而没有的材料（会议纪要、需求文档、上一版方案）问过用户。

提示词要求的：

- [ ] 先给出业务流 × 数据流的图谱，再展开分析。
- [ ] 有数据本体：关键对象、对象之间的关系、所处环节、状态变化。
- [ ] 每一类业务单元都走完了取数到写回的整条链，没有停在“推送”。
- [ ] 顺着每条链走一遍，看能不能真的跑通：
  - 自动提醒要用的数据，在提醒发生之前真的能进入系统；还要靠人工录入的，没有写成系统能自动发现。
  - 页面动作写回的对象和字段，在数据本体和建表方案里都找得到；同一个对象、同一个状态，前后定义一致。
  - 业务单元的来源、处理状态和特殊情况（如夜间、紧急、返修）分开了，没有把会同时出现的条件写成互相独立的来源。
- [ ] 写了事件表怎么建。
- [ ] 业务的说法落到了具体的技术端（如客户端、服务端、中台）上。
- [ ] 有对象关系图和流程图，架构师能直接对照。
- [ ] 需要验证的接口、字段、数据质量标了“待验证”。

范例体现了、提示词没有直接要求的（适合这次的由执行的 agent 补上；不适用的不硬套，也不为凑完整编数据）：

- [ ] 读者在开头就能拿到结论和全貌，不用读完全文。
- [ ] 需求落到了读者能开工的界面或接口，每个界面动作对应哪次写入。
- [ ] 写清了先做什么、为什么先做、做到什么算完。

事实：

- [ ] 访谈里的说法能在访谈报告里找到原话或出处。
- [ ] 每个统计数字写清了来源、样本范围和口径；样本不是全量时，没有给出看似全量的比例。
- [ ] 没有把技术推测写成已具备的能力。
- [ ] 每个数字的口径和局限都写清了，就近写或集中写一处都可以。

深度（对照深度框架的浅深对照）：

- [ ] 写得出读者要做的决定，每章都对应其中一个；章节是从本案推出来的，换一个业务场景不会一模一样。
- [ ] 过程数据被用来回答问题，而不是给结论配数字：至少有几处设计决定是从数据里的发现推出来的。
- [ ] 访谈里的量级说法用数据核过，不一致处两边都写了。
- [ ] 有一句话的主线和支撑它的发现，拿掉任何一个发现设计都会变。
- [ ] 对象写到字段和状态，规则写到阈值和配置项，页面写到组件、接口和交互，技术团队能直接开工。
- [ ] 每条链写清了本案的边界和反例（路觅案例里是夜间消息、群里谁是客户、重复识别、误报撤销，仅作参照）。
- [ ] 多业务线或多人群的差异用数据验证过，写清落在哪一层、哪些共用。
- [ ] 验收能用历史数据回放，有指标和阈值。
- [ ] 分析脚本已保存，报告里的数字都能复现。
- [ ] 独立审查已做，意见已改或写明不改的理由。
