# 内容验收与独立审核（第 5 轮用）

摘自 niuma-home `docs/策略规则/10-报告内容规格.md` **report-v2.1** 第 7.1、9 节与 `06-SCOUT-8运行规范.md` **scout-v1.1** 阶段 07。规则以原文为准。

两层质量检查分开：`quality.md` 的八项自检管研究层的事实和结构（第 1 轮）；本文管报告的**商业内容**（第 5 轮）。技术校验通过只能证明数据与规则合规，不能证明策略有洞察、能指导经营。

## 1. 六项评分（每项 0–5，总分 30）

| 维度 | 5 分标准 |
|---|---|
| 月度整体判断 | 准确概括周期、地区差异、主要机会与经营方向 |
| 地区需求洞察 | 不止描述节点，能解释用户任务、深层矛盾及购买机制 |
| 研究论证质量 | 关键结论有证据，能比较不同解释，准确说明不确定性 |
| 策略推导连贯性 | 从需求到机会、SKU、卖点和促销的逻辑完整 |
| 商业可执行性 | 方案符合资源、毛利、师资及实际业务能力 |
| 报告表达质量 | 结构清晰、重点突出、没有无意义的碎片化与重复 |

门槛（初始，试写校准）：**总分 ≥ 24，且每项 ≥ 3**。
**一票否决**（不以总分抵消，直接不通过）：关键事实错误；无依据的重大商业结论；无法兑现的服务承诺；违反毛利或交付约束的促销方案。

## 2. 五个强制验收问题（全部成立才有策略指导价值）

1. 只读第一章，能否准确理解本月主要经营形势和主攻方向？（不成立：总览与主线失败）
2. 读六地区分析，能否说清各地区需求差异背后的原因，而不只是复述校历？
3. 对照主推 SKU，能否指出它具体回应了前文哪一个已识别的需求或痛点？
4. 对照营销及促销方案，能否解释为什么采用这种机制而非其他方式？（3、4 不成立：后半部分是独立编写的营销建议，不是推导出的策略）
5. 读完整份报告，营销、销售、用户运营和师资团队是否知道本月应优先做什么？（不成立：没有形成经营行动方针）

## 3. 审核怎么做

- **审核方必须是新上下文**：Claude 会话用 Agent 工具开一个子 agent；Codex 会话开一个新会话。**不给** `synthesis.md`、`design.md` 和生成过程。
- **分两个视角、两次给材料**（GPT 2.0.0 审核 P1-05）：
  1. **视角一 · 管理者只读报告**：第一条消息只给 `report.md`、本文、`report-spec.md`（规格不是事实来源）。审核方像经营负责人一样读，先写下：用三五句话复述本月主线和主攻方向；五个强制问题逐条成立 / 不成立；哪里看不懂、哪里像套话、哪里推导断了；「月度整体判断」「策略推导连贯性」「报告表达质量」三项初评。写完再进视角二，**视角一的内容之后不改**，只能在视角二补充。
  2. **视角二 · 回查事实与产品资料**：第二条消息（Claude 用 SendMessage 续同一个子 agent；Codex 在同一会话发第二条）再给 `report-check.txt`、`digest.md`、`products.md`、背景卡情况。抽查至少 5 个事实（日期、学校、活动条款、能力卡）回到原文核对；核对报告等级和输入是否相符、卖点有没有超出能力卡、促销和现行活动有没有冲突、跨月权益口径；然后完成六项评分和一票否决，列出必须修改的问题（位置 + 问题 + 改法）。
- 两个视角结论不一致时（例如读起来通顺、回查发现关键事实错），以视角二为准，并在「必须修改」里写明。
- 一次审核 → 一次返修 → 返修后由**同一审核方**定向复核，只核上次指出的问题。复核后仍未解决的关键问题，写进交付答复交常浩裁决，不无限循环。
- 审核方无法执行（没有可用的独立执行方）：`review.md` 写「第 5 轮未执行」及原因，答复里照实说，**不能写成通过**；执行者自评的分数只能标「自评」。

## 4. 给审核方的简报模板

第一条消息（视角一）：

```text
你是月度用户策略报告的独立审核方，先像经营负责人一样只读报告本身。
材料：<report.md 路径>、<quality-content.md>、<report-spec.md>（规格只用来对照写法，不是事实来源）。现在不给其他材料，也不要去找。
任务：按 quality-content.md 第 5 节 review.md 模板写「视角一」：
1. 用三五句话复述本月主线、主攻方向和关键取舍（复述不出来就是问题）。
2. 逐条回答第 2 节五个强制问题：成立 / 不成立 + 依据（引报告原句位置）。
3. 列出看不懂、像套话、推导断开的地方。
4. 初评「月度整体判断」「策略推导连贯性」「报告表达质量」三项（0–5，各一句理由）。
写完把 review.md 存到 <工作目录>/review.md，回复「视角一完成」。之后不要改视角一的内容。
```

第二条消息（视角二，视角一完成后再发）：

```text
现在给你回查材料：<report-check.txt>、<digest.md>、<products.md>；业务背景卡：<填了哪几栏>；产品能力卡：<各 SKU 填了几项>。
任务：在 review.md 里接着写「视角二」：
1. 抽查至少 5 个事实（日期、学校、活动条款、能力卡）回到 digest.md / products.md 核对，写核对结果。
2. 核对报告头的报告等级与输入是否相符；卖点有没有超出能力卡；促销和现行活动有没有冲突、跨月权益口径对不对。
3. 按第 1 节六项各打 0–5 分（视角一初评的三项可以改，写明为什么），检查四条一票否决。
4. 列必须修改的问题（章节 + 问题 + 建议改法），按严重程度排序；不影响判断的单列为「建议」。
5. 结论：通过（≥24 且每项 ≥3、五问全成立、无否决）/ 不通过。
不看、也不要求生成过程；不要替执行者重写报告。
```
