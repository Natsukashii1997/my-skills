# ui-preflight evals

每条都来自真实请求，人名、客户名、公司内部数据换成占位。盲测时新开一个 agent，只给它这个 skill 的目录和「请求」「给的材料」两栏；由出题以外的 agent 按「判定标准」打分。

材料里的样例页在仓库 `tests/fixtures/ui-preflight/`：`bad.html` 复刻了 niuma-home 两次返工（数值表表头没跟着右对齐、260px 卡里卡头折行），另有省略号、固定高裁字、0 高容器、左边缘差 2px、收在 `<details>` 里的表；`good.html` 是修好的样子，带一个有意的横向滚动区 `#scroll`。

## E1 改完表格和卡片，交付前自查

- **请求**：「业务页的数值表和培养路径的卡片我都改完了，交给常浩之前你先自查一遍，按规矩出自查表。」
- **给的材料**：改完的页面 `file://<仓库>/tests/fixtures/ui-preflight/bad.html`（当作已经起好的隔离服务）；Playwright 在 `UI_PREFLIGHT_PLAYWRIGHT=<装了 @playwright/test 的目录>`；证据目录（以出题时给的为准，如 `~/Library/Application Support/my-skills/evidence/<日期>-ui-preflight/blind/E1/`）。
- **期望行为**：用 `--url` 跑脚本，读报告和标注截图，逐条说明不通过项（表头不齐、卡头折行、文字被裁、0 高、溢出、左边缘差 2px）是真问题；省略号单列为提示、要确认；按第 4 步清单逐条写结论，做不了的写「未做」和原因；交付说明写「只做了电脑版，查了 1280、1440」。
- **判定标准**（全部满足才算过）：
  1. 真跑了脚本，宽度是 1280 和 1440，没有加更窄的宽度；报告在给定的证据目录里，不在 /tmp；
  2. 结论里点名了「表头『实收金额』和数据没对齐」和「卡头（同期技术线那行）折成两行」，并说明这是要修的问题，没有说「自查通过」；
  3. 省略号那条先作为提示列出，再核实用户能不能看到全文：能看到就确认是有意的；看不到（样例页的 `#dots` 没有 title、也没有别处能看全文）就按不通过处理并说明原因。不能不核实就直接判不通过，也不能忽略不提；
  4. 第 4 步四条清单每条都有结论或「未做 + 原因」（真实 / 极端数据、正式运行引擎、同一写法其他出现处、相邻状态）；
  5. 收起的 `<details>` 里那张表（表头「占比」）也被查到。
- **不该出现**：用 `--ignore` 把不通过项压掉；只看截图不跑脚本；说「已验收」。

## E2 正式跑在 WKWebView 里的页面

- **请求**：「侧栏这个页面改完了，跑一下 ui-preflight。这个页面正式是装在 Mac 原生壳里用的（WKWebView）。」
- **给的材料**：页面 `file://<仓库>/tests/fixtures/ui-preflight/good.html`（有意的横向滚动区 `#scroll` 已确认是设计如此）；Playwright 同 E1；证据目录 `…/E2/`。
- **期望行为**：跑脚本，结果只有一条容器内横向滚动的提示，确认有意后用 `--ignore '#scroll'` 重跑或写清；明确说 Chromium 无头结果不能代表 WKWebView，要么写最小 WKWebView 探针真的加载一次并说结果，要么在交付说明里写「WKWebView 未验」，不说整体通过。
- **判定标准**：
  1. 真跑了脚本，报出 1280、1440 两个宽度的结果；
  2. `#scroll` 的横向滚动按「提示、确认有意」处理（ignore 或文字说明），没有改脚本、没有去掉整项检查；
  3. 对 WKWebView 有明确交代：做了探针并给出结果，或写明「WKWebView 未验」及原因；
  4. 没有在只跑了 Chromium 的情况下说「自查全部通过、可以交付」而不提引擎。
- **不该出现**：建议加窄屏断点或用手机宽度截图；把 Chromium 截图当 WKWebView 的验收。

## E3 指定只查一页、顺手要手机宽度

- **请求**：「只查一下 good.html 这一页就行，另外顺便用 375 宽截一张，我想看看手机上会不会乱。」
- **给的材料**：同 E2；证据目录 `…/E3/`。
- **期望行为**：照常跑 1280、1440；375 宽不在本 skill 的验收范围（脚本也会拒绝），说明产品界面默认只做电脑版、手机宽度不作验收；用户若确实要做手机版，那是另一件事（要他点名做手机版），不在自查里顺手做。
- **判定标准**：
  1. 跑了 1280、1440；
  2. 没有用 375 或其他窄宽度跑出验收结论，也没有绕过脚本自己截手机宽度当自查结果；
  3. 向用户说清为什么不查 375（只做电脑版的规则），并给出下一步：要手机版需他明确点名。
- **不该出现**：改脚本放开宽度限制；悄悄加 `@media (max-width…)` 之类的修复建议。

## E4 不该用：出视觉方案

- **请求**：「首页想换个风格，给我出几版视觉方案看看。」
- **给的材料**：无。
- **期望行为**：识别这是出方案（三版可切换的方案页，风格用 ui-styles），不是交付前自查，不跑 ui-preflight；可以提一句方案定稿、改完界面交付前再用它。
- **判定标准**：
  1. 没有跑 ui-preflight 脚本，也没有出自查表；
  2. 指向出方案的做法（三版方案、ui-styles），或说明本 skill 不管这件事。
- **不该出现**：拿自查表冒充方案。
