# 回信怎么处理、怎么收口

## 1. 驿窗怎么处理工程审查的回信

据驿窗 postpane#233 的实现（MA-02 契约第 4 节）：

- 驿窗看回信**倒数第二行**「审查出口：通过 / 返修 / 证据不足暂停 / 决策升级」和**最后一行**「结论：通过 / 需修改」。通过配通过，其余三档配需修改。
- 「通过」：结束接力。
- 「返修」且预算还有：把意见转回本会话（自动往返）。你改完再调用 `relay_to_chatgpt` 就是下一轮。
- 「返修」且预算用完（L1 第 1 轮、L2/L3 第 2 轮）：意见转回本会话，接力自动结束，末尾附「请按意见修改，在 PR 上写「补改未复审」后收口，不要再调用 relay_to_chatgpt」。
- 「证据不足暂停」：转回本会话并停止自动往返。补了证据再送会续上，那一次不计轮数。
- 「决策升级」：转回本会话并交常浩。
- 出口和结论对不上：不转回，交常浩。没写出口那一行：只看结论，按返修处理。
- 转回的消息可能在你已经处理完之后又到一次（例如你先从侧栏读到了回信）。先看 PR 上有没有同一审查版本的处理说明，有就不重复处理。

## 2. 逐条处理表

每条重要意见一行，收口说明和续审送审包都用它：

```
| 意见 | 处理 | 位置 / 证据 |
|---|---|---|
| P1-01 <一句话> | 采纳：<怎么改的> | <文件、函数、新增测试名> |
| P2-01 <一句话> | 不采纳：<反证> | <代码位置 / 规则出处 / 测试> |
| P3-01 <一句话> | 记为后续：<issue 号或交接位置> | — |
```

- 采纳的要能指到代码和测试。只说「已修复」，等于没写。
- 不采纳要给反证，不能只说「不同意」。确实拿不准的，交常浩，不硬改也不硬拒。
- 记为后续只用于 P2/P3。P0/P1 只能采纳或不采纳；想记为后续的 P0/P1 算没解决，按第 4 节交常浩。
- 审查方说「未独立复跑」的部分，在收口说明里写明是「沿用提交方结果」。

## 3. 收口说明（PR 评论）

**补改未复审**（返修且预算用完；或只剩 P2/P3）：

```
## 补改未复审

ChatGPT Lx 第 N 轮（驿窗 `<接力 id>`，审 `<SHA 前 7 位>`）：P0 a / P1 b / P2 c / P3 d，出口「返修」。逐条复核<都成立 / 其中 … 不成立>，补改提交 `<SHA>`。Lx 预算用完，按 MA-02 契约补改未复审收口。

<逐条处理表>

测试：
<命令 + 原样结果>
```

**审查通过**：

```
审查通过：ChatGPT Lx 第 N 轮（驿窗 `<接力 id>`，审 `<SHA 前 7 位>`），出口「通过」。<有 P3 建议就写怎么处理>。等常浩说「合并」。
```

## 4. 交常浩（决策升级、超预算后仍有 P0/P1、出口对不上）

给常浩的说明要能直接拍板：

```
<PR> 的工程审查停在 <出口 / 预算用完>，需要你定：
- 卡在哪：<剩下的 P0/P1，各一句>
- 选项（推荐放第一个）：
  1. <修完再复审一次（授权专项续审，只验 …）>：依据 …
  2. <收缩范围（拆小 PR、只合并已过审的部分）/ 重新设计 / 补证据 / 换审查手段>：依据 …
- 我的推荐和理由：…
请回复「<选项 1 的说法>」或「<选项 2 的说法>」。
```

- 选项只从契约第 8 节的去向里挑：修完后授权一次有边界的专项续审、收缩范围、重新设计、补证据、换审查手段。**「带着没解决的 P0/P1 合并」不列为选项**，也不放进推荐。
- 常浩自己提出要带风险合并：这是他的风险接受决定（L3 还要他明确授权动作）。照做前在 PR 上写清剩下的每条 P0/P1 和可能的后果，运行记录 `note` 写「常浩接受风险合并：<剩下的 P0/P1>」，`resolution` 按实际写。
- 交常浩期间不合并、不记运行记录（SKILL.md 第 7 节），常浩决定后再记，他的这次拍板计入 `owner_interventions`。

常浩选了续审，按 brief.md 第 3 节送，`extra` 写明是他授权的。

## 5. 运行记录样例

`/Users/nat/Documents/ChatGPT/个人/work/multi-agent/runs/runs.jsonl` 一行一条，**字段一个不少、一个不多**（`tests/runs-format.test.mjs` 会逐行检查）。下面是一条真实记录（agent-kit#46，合并后的状态）：

```json
{"run_id":"R-20261108-04","case_id":null,"mode":"MA-02","kind":"真实","title":"agent-kit 全局指令加多 Agent 路由一行","handoffs":["h1a1ba3fd6ee01"],"pr":"Natsukashii1997/agent-kit#46","risk":"L1","rounds":1,"exit":"返修","resolution":"补改未复审后合并","reported_p0p1":0,"verified_findings":0,"changed_decision":null,"baseline":"送审前作者自测：agent-kit node --test 58 项全过","over_budget":false,"split":false,"owner_interventions":0,"started":"2026-11-08 16:21","ended":"2026-11-08 16:24","evidence":"agent-kit PR #46 评论「补改未复审」，补改提交 1961543，合并 2911c84；驿窗 handoffs.json","note":"只有 1 条 P2，改成三段式触发后补改未复审；没有 P0/P1，所以 verified_findings 记 0"}
```

要点：

- `run_id`：`R-` + **`started` 的北京时间日期** + 两位序号，序号看文件里这个日期已有的最大号加一。跨天收口也用 `started` 那天，不用记录当天（格式测试会核对两者日期一致）。
- `case_id`：同一个任务走了几个模式（例如 MA-03 验证后再走 MA-02）时，几条记录写同一个 `C-<短名>`；只走 MA-02 写 `null`。
- `handoffs` 是数组（续审、代发产生的多个接力 id 都列上）；`rounds` 是整数，等于回信次数。
- `exit` 只用 `通过 / 返修 / 证据不足暂停 / 决策升级 / 未送审`。
- `resolution` 只用 `已合并 / 补改未复审后合并 / 未合并 / 进行中 / 不适用`；还没合并写 `进行中`，合并后改。
- `reported_p0p1`：回信报的 P0+P1 数；`verified_findings`：你复核成立、而且原本没发现的 P0/P1 数，拿不准写 null。都是整数或 null，不写字符串，不用 0 代替不知道。
- `changed_decision`：MA-02 一般写 `null`（这是 MA-01、MA-04 的价值口径）；审查意见确实让方案、假设或执行边界变了，写 `true` 并在 `note` 说明。
- `baseline`：送审前作者自己做到哪一步，写自测命令和结果，例如「送审前作者自测：node --test 58 项全过」；没记录写 `null`。
- `over_budget`：轮数超出本级预算（常浩授权续审）写 `true`，否则 `false`。为 `true` 时另在 MA-02 契约第 7 节追加一行。
- `split`：同一验收目标另开了新单、重置了轮数写 `true`，否则 `false`。正常流程永远是 `false`；为 `true` 说明有违规，`note` 写清原因。
- `owner_interventions`：常浩介入的次数，只算**拍板**（超预算后的去向、风险接受、决定 L1 跳过送审）、**授权续审或手动续审**、**流程外的要求**（例如流程没要求时他额外要求送审）。按流程本来就该做的送审、常浩说「合并」都不算。样例 R-20261108-04 是按流程送审、补改后合并，记 `0`。
- `kind`：真实使用写 `真实`；判断后决定不送的写 `未协同`。
- `started` / `ended`：北京时间 `YYYY-MM-DD HH:mm`，取第一次送审和最后一条回信。
