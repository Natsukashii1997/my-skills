# 提案.md 的格式

写在扫描输出目录下，和 `signals.md` 放在一起。整份文件给用户本人看，不外发。

## 骨架

下面骨架里的次数、行号、会话数都是虚构的示例，不对应任何真实统计。

```markdown
# 会话复盘提案：2026-10-30 至 2026-11-05

- 覆盖：Claude Code 12 个会话、Codex 8 个会话；项目 proj-alpha、proj-beta
- 缺口：扫描状态 partial，原因是 Codex 有 1 行坏记录（不影响结论）
- 对照过的规则：~/.claude/CLAUDE.md、~/.codex/AGENTS.md、agent-kit/LESSONS.md、proj-alpha/docs/LESSONS.md
- 结论：A 3 条、B 2 条、C 1 条、D 1 条；最值得批的是 A1（同一件事纠正了 3 次）

## A 规则提案

### A1 改代码前先确认统计口径 · 新增 · 多次 / 跨会话
- 记录落点：~/.claude/CLAUDE.md 和 ~/.codex/AGENTS.md（两边各加一条）
- 建议原文：
  > - 涉及统计、汇总的改动，先用一句话复述口径（按周还是按月、含不含退费），用户确认后再改代码。
- 依据（共 3 次）：
  - 「不对，我说的是按周汇总，不是按月……」— ~/.claude/projects/-Users-demo-proj-alpha/1111….jsonl:11（2026-10-30 10:02）
  - 同一句话第二天又说了一次 — …0002.jsonl:2（2026-10-31 11:00）
- 现有规则对照：无相近规则（match 最高 0.21）
- 建议层级：〔文字〕
- 理由：要不要先复述口径取决于具体需求，机器判不了，〔结构〕〔机检〕〔体检〕都做不到
- 执行落点：无（文字层）
- 验证方式：无（文字层；看之后的复盘里还有没有同类纠正）
- 为什么值得写：同一误解跨了两个会话，每次返工约半小时

### A2 发通知只留 notify() 一个入口 · 已有但没被遵守 · 多次 / 跨会话
- 记录落点：proj-alpha/docs/LESSONS.md（记一条，说明为什么只留一个入口）
- 建议原文：删掉 `sendMail()`、`pushMessage()` 两个直接发送的旧函数，调用方全部改走 `notify()`；去重和静默时段只在 `notify()` 里判断
- 依据（共 2 次）：
  - 「又绕过 notify 直接 sendMail 了，夜里把用户吵醒」— …0003.jsonl:20（2026-11-01 09:30）
- 现有规则对照：proj-alpha/AGENTS.md:12 已写「发通知走 notify()」，AI 还是照着旁边的旧代码直接调了 `sendMail()`
- 建议层级：〔结构〕（从〔文字〕直接升上来，不经过〔机检〕）
- 理由：旧函数还在，Agent 照着附近的代码抄就会绕过；删掉之后这个错误写不出来，比加 lint 去拦更彻底
- 执行落点：proj-alpha 的 `src/notify/`：取消 `sendMail()`、`pushMessage()` 的导出，迁移全部调用方
- 验证方式：仓库里搜不到这两个函数的调用；把那次绕过的改动在新代码上重放，构建直接失败

## B 坑提案

### B1 proj-alpha 测试依赖 report-utils 本地包 · 新增 · 单次，待验证
- 记录落点：proj-alpha/docs/LESSONS.md
- 建议原文：（按该文件现有条目的格式写：现象 → 原因 → 怎么做）
- 依据：`Bash: npm test` 连续失败 3 次，报错 Cannot find module 'report-utils' — …0001.jsonl:4 至 :8（2026-10-30 10:00）
- 现有规则对照：无
- 建议层级：〔机检〕
- 理由：〔结构〕（改成工作区依赖）要动包管理方式，超出这个坑的范围
- 执行落点：proj-alpha 的 `npm test` 前置检查 `scripts/pretest.mjs`：report-utils 没链接就报「先在 report-utils 目录跑 npm link」
- 验证方式：去掉 report-utils 的链接后跑一次 `npm test`，看到的是这句报错，而不是 Cannot find module

### B2 proj-beta 模拟器偶发启动超时 · 新增 · 单次，待验证
- 记录落点：proj-beta/docs/LESSONS.md
- 建议原文：（现象 → 原因 → 怎么做：重跑一次即可）
- 依据：`Bash: xcrun simctl boot` 超时 1 次，重跑通过 — …0004.jsonl:31（2026-11-02 16:10）
- 现有规则对照：无
- 建议层级：〔提醒〕暂不建议升级
- 理由：只出现过一次，只在当前 Xcode 版本出现，重跑就好，复发代价低，为它写检查不值得；同类再出现时重新评估
- 执行落点：无（只靠「触发」关键词提醒）
- 验证方式：无

## C 决定

### C1 所有 PR 由常浩本人审 · 已有但没被遵守
- 落点：Vault（目录待定）；另见 A3
- 记录内容：2026-10-30 定：所有 PR 由我审，AI 不自行合并。原因：……（会话里没说原因就写「未说明」，不要编）
- 依据：「这次改动先别合并，定了：所有 PR 都由我来审」— ~/.codex/sessions/2026/10/30/rollout-….jsonl:5（2026-10-30 14:00）
- 现有规则对照：~/.claude/CLAUDE.md:5 已写「所有 PR 由常浩审，AI 不自行合并」。同一天 AI 仍尝试 `git push origin main` 被拒（R1、R3），是执行问题，见 A3（A3 的建议层级是从〔文字〕升到〔机检〕：执行落点是在执行前拦下推送 main 的 hook）

## D 自动化

### D1 「合并」不再停下来等常浩回 · 多次 / 跨会话
- 重复信号：S1「合并」40 次（输入框 15、驿窗侧栏 25），等于按钮 37、等于推荐 36，27 个会话
- 常浩在替 AI 做什么：AI 已经判断该合并、写好推荐按钮，再停下来等他点一下
- 建议做法：〔改规则〕把「合并要常浩说合并」改成按合并策略交 Hermes 合并，只有例外才停（例：agent-kit#122 的合并放权）
- 落点：《工程流程》第 5 节；全局指令第 5 节接手会话那段
- 怎么量：下一期复盘里 S 组「合并」的次数和「等于推荐」的占比
- 注意：要改的是已定内容，按第 15 节先发改动确认

## 已覆盖（不出提案）
- 「表头用中文」：proj-beta 的 CLAUDE.md 已有

## 筛掉的信号
- 共 9 条：6 条是正常需求调整，2 条是弱信号误报，1 条只针对一次具体产出
```

## 写法要求

- **编号**：A1、A2……按重要性排，不按时间排。B 类跨项目的条目写「G-??」，真正的 G 编号由用户批准时定。
- **建议原文**：照落点文件现有的语气和格式写，写成规则本身（「做 X 之前先 Y」），不要写成复盘叙述（「上周 AI 犯了……」）。一条只讲一件事。
- **依据**：原话只用 `signals.md` 里的脱敏片段，可以再删短，但不能改写意思。出处照抄 `文件:行号（时间）`，路径写全，用户要能顺着找回原文。用 `context` 子命令查到、`signals.md` 里没有的行，出处后面标「（context）」。
- **不编**：会话里没说原因、没说范围的，写「未说明」，或列为待用户补充，不替用户补理由。
- **一句话两用**：同一句话既是 C 决定又是 A 规则时，两条都写，互相注明，依据可以只写一次。
- **已有但没被遵守**：不要再提一条同样的规则。写清规则在哪个文件第几行，违反发生在哪里。现有机制本来就在〔结构〕〔机检〕〔体检〕层的，先查它有没有执行、为什么没拦住，能在同一层修好的先修；否则从〔结构〕往下重新选最高做得到的层，不要求逐级升（例 A2 从〔文字〕直接到〔结构〕）。只有判断题升不上去时，才改成挪到更醒目的位置或写得更具体。
- **引用重复次数**：第四节每一组（S 编号）的全窗口次数，在提案里第一次写到的地方，次数后面照抄那一行括号里的来源拆分，例如 S1「合并」40 次（输入框 15、驿窗侧栏 25）；汇总表里逐组列出的，就在那一格写。之后再提同一组、几组合起来的合计、分段补扫的前后段次数、全部组的总数，只写数字。对话里的回复同理：每组第一次写到全窗口次数时带拆分，只写合组合计（「放行类 50 次」）不算写到了这一组。交付前用 `check` 子命令查提案文件。
- **D 自动化**：来自 `signals.md` 第四节「重复」。每条写：重复信号（列出涉及的每个 S / L 编号；单组的写次数、等于按钮、等于推荐几次（为 0 也写），这是它第一次写到全窗口次数时，按上一条带来源拆分；几组合成一条的写合计、合计里等于按钮和等于推荐各几次（为 0 也写），各组的来源拆分写在第一次写到它们的地方，这里不重复；L 组没有来源和按钮数据，写条数和会话数即可）、常浩在替 AI 做什么（一句话）、建议做法（三选一：〔改规则〕让 AI 不再停在这里，〔做成 skill〕，〔做成钩子或定时任务〕）、落点、怎么量（下一期同一句的次数）。等于推荐占比高的短话，优先考虑〔改规则〕：AI 已经有答案，停下只是在等点头。只出提案，规则、钩子、定时任务一样不改；碰到已定内容的，注明要先发改动确认。全局指令（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）、项目 `docs/DECIDED.md`、项目 AGENTS.md 里的约定（例如某仓库停用 CI）、《工程流程》、ADR、合并策略和它的安全约束，都算已定内容，改它们的每一条 D 类都要注明。
- **层级五项**：A、B 类每条都写「建议层级 / 理由 / 记录落点 / 执行落点 / 验证方式」（C 类不写）。记录落点是知识记在哪（LESSONS、CLAUDE.md、AGENTS.md），执行落点是防错实际做在哪（〔结构〕写要改的接口、目录或调用路径，〔机检〕写检查脚本、hook 或 CI 步骤，〔体检〕写体检项，〔文字〕〔提醒〕写「无」），两者不要混。A 类只有层级是〔文字〕时才把规则写进 CLAUDE.md / AGENTS.md。〔提醒〕表示「暂不建议升级」，理由里要写清是证据不足、复发代价低、只在当前环境成立，还是常浩已定不升级，不要为了填满字段硬凑一个检查。
