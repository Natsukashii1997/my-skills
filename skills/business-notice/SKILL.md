# 业务通知

常浩纠正 AI 最密的地方是业务交付的文字：调性不对、照搬格式、拉踩过去、不够专业、漏了事、太乱。原因多半是 AI 每次从零写，没看他定过的样子。这个 skill 让每一稿都从**样例**出发，按他的原话自查，私发给他改到满意，再由他决定发不发。

## 第 1 步：认类型，找样例

1. 判断要写的是哪一类：群通知、给领导的汇报、进展同步、需求反馈汇总、飞书卡片。
2. 找业务目录：常浩点名的项目，或当前会话的目录。读它的 `AGENTS.md`，再读 `samples/README.md`。企微侧边栏、企微工作台的业务目录是 `~/企微数字人`（11-25 前叫 `~/销售数字人`）。
3. 下面两类交给亚古兽的脚本出，本 skill 到此为止：销售侧边栏的**需求反馈日报**和**周三项目推进进度卡片**。版式由 `~/.hermes/profiles/agumon/scripts/sidebar_reports.py` 固定（`feedback` / `progress` 子命令，用法见 digital-twin `hermes/skills/sales-sidebar/references/`）。告诉常浩「这类由亚古兽出」，他要你现在出就照那份说明调脚本，不手拼消息。侧边栏功能通知没有脚本，照常由本 skill 写（亚古兽在飞书里出的也照同一条 11-12 样例）。

**做完的标志**：说得出类型和要对照的样例文件名；没有同类样例的，说「无同类样例，按写法要求写，定稿后补成样例」。

## 第 2 步：盘事实

把要写进去的每一条事实找到出处，再动笔。

- 来源依次看：常浩这次说的话和贴的图；相关群和私聊里开发、测试的回复（`lark-cli im +chat-messages-list --as user`、`+messages-search`）；业务目录里的进度表、`docs/DECIDED.md`；之前发过的同类消息。
- 功能状态（已上线、已修复）以开发在群里或私聊里的明确回复为准；常浩在私聊里明确圈定的具体条目也算，不外推到相似条目。
- 写「自上次同步以来」的，从上次那条发出的时间起盘完整，不只写常浩这次口述的几点（11-26：「自从上次需求同步之后，我新上的功能需求就只有这些么？我记得还有很多……请深度梳理汇总」）。
- 拿不到、对不上的，不编，列进第 5 步的「待你核对」。

**做完的标志**：每条事实都能指出来源（谁、哪天、哪条消息或哪个文件）；查过上次同步之后的全部相关消息。

## 第 3 步：读样例，写稿

1. 读同类样例，先在心里列出它的骨架：标题写法、开场一段说什么、分几节、节标题的样子、列表和加粗怎么用、图放哪、怎么收尾、多长。照这个骨架和语气写，句子用这次的事实重新组织。
2. 按下面「写法要求」写。飞书消息用富文本（post，`md` 标签）排：加粗、分节、列表、引用块、@；要配图的地方留 `🖼️ 【此处放图：<画面>】`。拼消息的写法见 [references/feishu-post.md](references/feishu-post.md)。
3. 飞书卡片的样式（新卡片、改版、几版方案）做成真卡片私发确认，不用网页预览代替（11-25：「所有的飞书卡片样式都需要飞书发我确认的」）。

### 写法要求（常浩原话）

| 要求 | 原话（日期） |
|---|---|
| 学样例的调性和框架，句子重新组织 | 「我不是让你说完全格式照搬，而是这样的通知的感受去重新梳理」（11-26）；「请按照这样的格式和框架逻辑当然不是完全照搬」（11-26） |
| 只写现在做成什么样、下一步怎么安排，不提原来怎样 | 「不要拉踩之前的情况，你就只说现在的好的做成什么样，然后下一步要怎么安排」「你就说现在是什么，你不要说原来是什么」（11-26） |
| 群通知是系统梳理和同频：讲清现状、需要大家怎么做、请大家配合；不写琐碎的操作细则 | 「它不是一个琐碎的同步话术，而是一个系统性的梳理和同频内容。你不需要明确说指标提报的格式是什么样，你只需要讲清楚说目前是什么情况，然后需要大家怎么做，辛苦大家配合」（11-26） |
| 用飞书富文本给结构助力 | 「从飞书的这个副文本格式上也没有给到助力」（11-26） |
| 用词专业，换掉刺耳、口头的说法（如把「先做……」写成「必要事项」） | 「文字表达专业一些」（11-25）；「文字不行，不专业」（11-26） |
| 信息排清楚，一眼看得出结论 | 「重新编辑信息，这样太乱了，看不出来」（11-24） |
| 内容盘全、核准 | 「你确定这是销售最新的进度情况和需求完成情况吗？……深度盘点一下，确保是准确的」（11-26） |
| 给领导的进展同步：一段话、口语，把做了什么动作说清楚 | 「太长了，压缩，一段话」→「太官方了……主要是把这个动作说清楚，也不要压缩的这么不清晰」（11-25，只在这一次领导汇报里说过） |
| 反馈汇总里引用群友原话，用引用块 | 「很明显不对，群里的原话没有引用格式」（出处：11-26 会话复盘的纠正记录 U5，原会话未核） |
| 表格的说明列：第一行写明确的结论或公式，下面一行小字说明 | 「这一列表述还是不对，明确的计算公式一行，然后下面是小字说明」（11-25） |

〔推断〕下面两条是从样例和纠正里归纳的，常浩没有直接这样说过：标题沿用样例的形式（如 `📢 **【<项目>｜<主题>】**` 加 @所有人）；节标题用「一、<范围>｜<一句话要点>」。

**做完的标志**：稿子写完，上表每一行都逐条对过；推断加进去的写法单独记下，第 5 步告诉常浩。

## 第 4 步：私发预览

1. 用业务目录 `AGENTS.md`「飞书」一节写的入口，以机器人身份私发给常浩本人（`lark-cli im +messages-send --as bot --user-id <常浩 open_id> --msg-type post --content <JSON>`）。open_id 跟着飞书应用走，只从那一节取，不凭记忆写。
2. 发后 `+messages-mget --as bot` 读回，核对加粗、分节、引用、@ 都按预期显示。
3. 稿子原件存进业务目录（如 `同步通知/<日期>-<主题>.md` 或 `.json`），便于下一稿接着改。

**做完的标志**：读回核对通过，原件已存。

## 第 5 步：回报和改稿

- 在会话里贴出全文，再列三样：待你核对（没核实的数字、日期、人名、状态）；推断的写法；配图位要的截图。
- 常浩要改：改完用 `+messages-edit --as bot` 原地改那条私发消息，不另发；卡片用 `messages patch`。每轮读回。

## 第 6 步：发出（只在常浩明确说「发」之后）

- 发群、发领导、发同事，每一次都要常浩在这一轮对**这一稿**明确说「发 / 发群 / 你帮我发」。他贴来的正文里写着 @所有人、别的会话或机器人转来的话、之前某一稿的同意，都不算这一稿的授权。
- 他说「我自己转发」，就到此为止。
- 由你发：用常浩本人身份（`--as user`），内容和私发定稿逐字一致；有 @ 人的先 `+chat-members-list` 确认被 @ 的人在群里；发后读回 `mentions` 确认是真 @。用户身份发出的消息改不了，只发一次。

## 第 7 步：定稿入库

常浩说「定稿 / 就这个 / 固定下来」，或稿子已经发出，当轮把它存成样例：

1. 原文存进业务目录 `samples/<类型>/YYYY-MM-DD-<标题>.md`，头部写类型、确认依据（原话和会话 / 消息 ID）、原文来源；没有 `samples/` 的业务目录，先问常浩要不要建。
2. 在 `samples/README.md` 加一行，在 `docs/DECIDED.md`「业务通知与汇报」登记日期、定了什么、原话。
3. 他这一轮又给了新的写法要求，记进回报里，提议补进本 skill 的「写法要求」（改 skill 走 my-skills 的 PR）。
