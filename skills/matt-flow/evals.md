# matt-flow evals

请求按常浩的说话习惯写，项目用他真实在做的项目，内部数据没有出现。条目数超过模板建议的 5 条：2.0.0 按三份评审补了多轮情景和触发测试（my-skills#86），常浩已同意。

覆盖：
- 第一轮：0 档（E1）、1 档（E2）、2 档含前置检查（E3）、3 档（E4）、半路入口（E5a）、只跑命令（E5b）。
- 多轮：1 档第二轮（E6）、2 档到了只能手动的站（E7）、跨会话「下一步呢」（E8）、中途插进无关 bug（E9）、「一口气做完」（E10）。
- 边界：交给别的 skill（E11）、已定内容（E12）。
- 真实触发测试（T 组）：不告诉答题者用哪个 skill，看描述能不能自己触发对。

E5、E11 下面各有两条，分开跑、分开判，两条都过才算过。

**盲测做法**：
- **E 组**：新开一个 agent，只给它去掉 evals.md、CHANGELOG.md 的 skill 副本，以及「请求」「给的材料」，让它写出这一轮会做什么、回什么（含要调用的技能、要读的文件、要跑的命令）。
- **T 组**：另开一个 agent，只给它一份可用技能清单（名字 + description，含 matt-flow 和容易撞车的技能）和请求，不说要用哪个，让它说会调用哪个技能。
- 两组都由出题以外的 agent 按「判定标准」打分。

## E1 0 档：错字

- **请求**：数码世界首页的标题「数码宝贝世界」打成了「数码宝贝事界」，帮我改一下
- **给的材料**：项目 `~/Documents/ChatGPT/个人/work/digiworld`，已有 AGENTS.md，已接 GitHub，配置齐全；会话开在这个项目的一个 worktree 里。
- **期望行为**：一句话说明是 0 档，在本地分支上直接改、自己验；改完停下，一次确认「开 issue、推送、开 PR」。
- **判定标准**：
  1. 判为 0 档，用一句话给出理由。
  2. 不问「开始吗」，直接动手改。
  3. 不调用任何 Matt 技能，不做前置检查。
  4. 改动在本地分支上，不直接提交到 main。
  5. 收尾三项：状态不是〔已结束〕（改动还没合并），「下一步」请常浩确认开 issue、推送、开 PR，且是一次确认。
- **不该出现**：先追问需求；跑 setup-matt-pocock-skills 或 project-starter；没问就建 issue 或推送。

## E6 1 档第二轮：答完问题后连着做

- **请求**：都按推荐
- **给的材料**：接 E2。上一轮已判 1 档，在 worktree 的本地分支 `claude/checkup-last-run` 上，起点提交 `abc1234`。问了 3 题（显示格式、看不出时怎么写、在哪里验证），常浩全按推荐。改动还没提交。my-skills 的 AGENTS.md 要求：改 skill 要升 `metadata.version`、写 CHANGELOG、重跑 evals。
- **期望行为**：连着做完 tdd、本地提交、审查（以 `abc1234` 为起点，确认改动不为空），审查结果修掉，再做 my-skills 的交付步骤，最后停下来一次确认「开 issue、推送、开 PR」。
- **判定标准**：
  1. tdd 和审查之间不停下等回复。
  2. 审查前先本地提交（或明确把未提交的改动纳入比较），比较起点用 `abc1234`，不问常浩要起点。

  4. 提到升版本、写 CHANGELOG、重跑 evals，并放在审查之后、开 PR 之前。
  5. 推送和开 PR 之前停下，写成一张确认清单；状态〔等你决定〕。
- **不该出现**：没问就推送或开 PR；审查比的是空改动；每做完一步就停。
