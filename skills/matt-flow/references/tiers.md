# 档位判定

按「做完之前还要决定多少事、要不要跨会话」判，不按常浩说话的语气或字数判。各档路线只在 SKILL.md 第 2 节写，这里只写判据、例外和每档的做法细节。

## 判据

| 档 | 判据（满足就是这一档） | 不是这一档的信号 |
|---|---|---|
| 0 档 · 顺手改 | 改一两处；没有要常浩决定的事；改完一眼能验（错字、文案、常浩点名要改成的值、一行明显的修正） | 要先问常浩「你想要哪种」；会改出他没点名的行为变化；碰到多个文件的逻辑 |
| 1 档 · 轻量 | 能一句话说清「做完是什么样」；改动集中在一个模块或一个页面；一个会话做得完；不需要新的数据格式或页面流程 | 一句话说不清；要拆成几块分别做；要改数据格式或跨多个模块 |
| 2 档 · 标准 | 需求还模糊（有几种理解、要做取舍），或要改多处（跨模块、多个页面、改数据格式、加新流程） | 连「做到什么样算完」都定不下来、要先做一串决定 → 3 档 |
| 3 档 · 大雾 | 全新项目（还没有代码仓库），或方向不清的大工程：不知道从哪下手，要先做很多决定才写得出需求文档 | 新项目但一句话说得清、一个会话做得完的小工具 → 按 1 或 2 档判（wayfinder 原文：只用于一个会话装不下、看不清路的工作） |

改动碰到常浩定过的东西（外观、文案、交互、流程等），不管几档，先按全局规则第 15 节单独确认，问完就停。

## 正反例

- 0 档：「首页标题的错字改一下」「按钮颜色改成 #1F6FEB」「把超时从 30 秒改成 60 秒」（他点名的值，不算没点名的行为变化）。
- 0 档的反例：「按钮颜色改一下」但没说改成什么 → 先问；「把侧栏动态小人换成静态图标」→ 动了定过的外观，先做第 15 节的改动确认。
- 1 档：「体检报告每个任务再加一列『上次运行时间』」「导出按钮再支持 CSV」。
- 1 档的反例：「报告再加一列，顺便把整个报告改成按项目分组」→ 两件事、要取舍，2 档。
- 2 档：「数码世界加个功能：问一个问题能同时查知识库和聊天记录」「给工作台加登录和权限」。
- 2 档的反例：「做个个人记账系统，还没想好要哪些功能」→ 新项目且方向不清，3 档。
- 3 档：「做一个家庭财务系统，管信用卡、房贷、教育金，还没想好要哪些功能、做成什么样」「把整个工作台从网页搬成 Mac App」。
- 3 档的反例：「新建一个小脚本，每天把下载文件夹里的截图挪到桌面」→ 新项目但一句话说得清，1 档。
- 不进本 skill：「我有个想法：每周一自动汇总飞书周报发给我」→ 业务流程要不要用 AI，用 ai-landing-method；「早报今天没发」「飞书机器人没反应了」→ 先用 automation-checkup 只读体检，查出是代码 bug 再进 diagnosing-bugs。

## 拿不准时

- 在两档之间拿不准：按**高一档**用一句话问常浩，并在那句话里说明「也可以按 X 档轻量做」。
- 在 0 档和 1 档之间拿不准：按 1 档做；那一轮如果发现没什么可问的，说明一句，跳过提问直接进 tdd。
- 修 bug 先看是不是半路入口：原因不明、时好时坏、昨天还好今天坏了 → diagnosing-bugs；原因一眼看得出、改一处就好 → 0 档（能补回归测试就补）。

## 升档、降档

- **升档**：走 1 档时发现要改多处、要做取舍，停下来用三选一问常浩，每项写清代价：
  1. 缩小范围留在 1 档（写明砍掉什么）；
  2. 升 2 档（已经问清的不重问，从 grill-with-docs 补问剩下的，问清了也可以直接写需求文档）；
  3. 先停。

  已经写了的测试和代码，在本地分支上提交保留。走 2 档时发现方向整个看不清，同样三选一问要不要升 3 档。
- **降档**：发现比想的小，说一句「这件事比预想的小，改按 X 档走」直接降，不用等回复。
- 常浩指定的档位优先；他说「这个简单，直接做」就按他说的，风险大的地方在收尾里写明。

## 各档的做法细节

### 0 档
在本地分支上直接改、自己验。改完一次确认「开 issue、推送、开 PR」（SKILL.md 第 7 节第 7 条）；项目允许直接进 main 的纯文档改动按项目约定。不调用 Matt 技能。

### 1 档
1. 从 `origin/main` 开本地分支（会话已在 worktree 里就在里面开；在主目录的，先建 worktree，不在主目录切分支），记下起点：`git rev-parse HEAD`。不是 git 仓库的，先问常浩要不要 `git init`；不要的，跳过审查并在收尾里说明。
2. **只借用 grilling 的问法，不加载 grilling 技能**：一轮、最多 3 个关键问题，编号，每题带推荐答案，常浩答「是」就是按推荐。本 skill 的「一轮」限制优先于 grilling 原文的「问到 frontier 为空」。tdd 要确认的接缝用白话并进这一轮。
3. 常浩答完后连着做，中间不停：
   - **tdd**（`mattpocock-skills:tdd`）：一次一个小切片，先写会失败的测试，再写刚好通过的代码；接缝用第 2 步确认过的。没有测试接缝的改动（文档、提示词、skill 正文），改用项目自己的验证方式，例如 my-skills 的 evals 盲测。
   - **本地提交**：本地提交不算对外写入，不用问。
   - **审查**（`mattpocock-skills:code-review`）：比较起点用第 1 步记下的提交，确认 `git diff <起点>...HEAD` 不为空。Spec 那一轴的需求来源就是第 2 步的问答结论，直接交给它；不要求先跑 setup-matt-pocock-skills。
   - 审查提出的问题修掉（不再复审，交付时写明「审查后的修正未复审」），再走项目要求的交付步骤（如升版本、写 CHANGELOG）。
4. 停下来，一次确认「开 issue、推送、开 PR」。

### 2 档
- 第一次走 2 档的项目，先做 SKILL.md 第 5 节的前置检查，作为第一站。
- **grill-with-docs 收尾时判一次**：剩下的活一个会话做得完 → 在本会话用 implement 实现，跳过 to-spec 和 to-tickets，在下一站卡片里写明为什么跳过；做不完 → 走完整路线。最后一轮问题、grilling 原文要的「共识确认」和这个判断，放进同一条消息里，不分三次停。
- **prototype**：
  - 界面问题按常浩全局规则第 9 节：三版明显不同的方案做进同一个 HTML 页面，一键切换，用 Artifact 发布，给 claude.ai 链接；只有必须用真实数据才能判断时，才在应用里用 `?variant=` 切换。
  - 逻辑问题做成一个可点着玩的 HTML，同样用 Artifact 发链接。
  - 原型分支推送、在 issue 上留指针，都算对外写入。
  - 原型的结论、分支或链接、相关决定和没解决的问题，写进需求文档或交接卡。
- **to-spec**：先写出需求文档草稿，再把三件事并成一次确认：测试接缝（用白话）、发不发需求 issue、草稿里补的默认值（问答里漏了、写的时候才发现的小点）。确认完再定稿。常浩原话里的限定词（如「放在项目目录下」）原样写进文档。这里确认过的接缝，就是之后 tdd 的事先约定接缝，实现时不再问。
- **to-tickets**：「拆法对不对」「发哪几张卡」「一张张做还是多个 AI 并行做完」并成一次确认；没有 GitHub 的项目，再加一项「每张卡审查通过后并入本地 main」。推荐：卡在 3 张以内，或常浩想每张都看一眼 → 一张张做（implement）；卡多、彼此独立 → 多个 AI 并行做完（implement-spec）。
- **开第一张卡之前，让 worktree 看得到前几站的产出**：
  - 有 GitHub 的项目：需求文档和任务卡在 issue 上，worktree 里查得到；前几站改的 `GLOSSARY.md`、`docs/adr/` 随第一张卡的分支一起提交，在 PR 说明里写明，不往 main 直接提交。
  - 没有 GitHub 的项目：本地 main 就是各卡的起点，把 `.scratch/<功能>/`、`GLOSSARY.md`、`docs/adr/` 本地提交进 main 再开卡（本地提交不用问）。
- **逐张实现（implement）**：
  - 每张卡开工前从 `origin/main` 开 worktree 分支 `claude/<卡号>-<短名>`，记下起点，不向常浩要起点。
  - implement 内部已经调 tdd 和审查；审查前先本地提交，保证改动不为空。
  - 审查提出的问题修掉后不再复审，交付时写明「审查后的修正未复审」，靠新增测试和全量测试兜底。
  - 一张卡一个 PR，`Closes #卡号`，推送和开 PR 前确认。没有 GitHub 的项目按 SKILL.md 第 7 节第 7 条，在本地并入 main。
- **多个 AI 并行做完（implement-spec）**：
  - 一条集成分支、一个 PR 关闭全部卡；末尾统一审查一次。
  - 子 agent 不推送、不开 PR、不关 issue，这些写入由主会话列清单确认后再做。
- to-spec 写完是 thinking-review 的检查节点。

### 3 档
- wayfinder 画地图、逐张解决决策卡：一个会话一张，研究类除外。地图和决策卡的建、指派、评论、关闭都算对外写入，按 SKILL.md 第 7 节第 3 条列清单确认。
- 定下目的地和地图时，是 thinking-review 的检查节点。
- 地图清了就并入 2 档，从 to-spec 开始。
- wayfinder 第 2 步如果发现根本没有雾（路已经清楚、一个会话做得完），按原文停下问常浩，通常改按 2 档或 1 档走。
