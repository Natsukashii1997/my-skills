# 自动化体检

常浩本机跑着一堆自建自动化（飞书网关 Hermes、数字分身、牛马之家、路觅的营销任务等），挂了往往不会第一时间发现。这个 skill 把它们全部过一遍，用一页报告说清楚：哪些要马上处理，哪些留意一下，哪些正常，以及比上次体检多了什么、好了什么。

分工：
- **脚本**做确定性的检查和判档：读配置文件、launchd 状态、日志时间，从日志里提炼常见原因。
- **agent** 把报告讲成人话，核实「该跑没跑」是不是因为电脑睡眠或关机，处置时逐条确认。
- **常浩**决定处理哪几条，以及要不要某个任务。

## 一、跑体检

```bash
S=~/.claude/skills/automation-checkup/scripts      # Codex 用 ~/.agents/skills/automation-checkup/scripts
python3 $S/checkup.py
```

- 报告写到 `~/Documents/自动化体检/自动化体检-日期时间.md`，同目录另存一份同名 `.json`（给 agent 读，也给下次体检做对比）。两份文件都只有本人能读。
- 终端会打印报告路径和三档计数。
- `--stdout` 只打印、不写文件；`--out 路径` 指定位置（已存在、但不是体检报告的文件不会被覆盖）；`--no-hermes`、`--no-crontab` 跳过对应检查；`--config 路径` 叠加一份临时配置。
- 只需要 macOS 自带的 python3，不装任何依赖。

## 二、跑完怎么回复

1. **先核实「该跑没跑」**。报告里有「X 天没跑」「X 小时没跑」时，先只读查那段时间电脑开着没有：

   ```bash
   pmset -g log | grep -E ' (Sleep|Wake|DarkWake) ' | tail -40
   last reboot | head -5
   last shutdown | head -5
   ```

   和睡眠、关机时段对得上的，告诉常浩「多半是电脑当时睡着或关着，不用处理」，并说明这是推断。对不上的才当真问题讲。

   要点：
   - 每隔 N 分钟跑的任务，睡眠期间错过的不补跑。
   - 按日历跑的任务，睡眠期间错过的醒来后补跑一次。
   - 关机期间错过的，两种都不补。

2. **一句结论加报告路径**。例如「3 个自动化停了或失败了，另有 6 项配置问题和 5 项提醒；比上次新出现 2 个问题」。
3. **「需要处理」逐条讲**。编号一律沿用报告里的编号，常浩说「处理 3」时才对得上。每条讲清四件事：
   - 是哪个自动化：用报告里的中文名。
   - 出了什么事。
   - 原因：报告里有「原因」就用它，没有就说「日志里看不出原因」。
   - 影响什么：配置里登记过「坏了影响」的照搬；没登记的写「推断：…」。

   日志原文只挑能说明原因的一行，不整段贴。
4. **「注意」挑会影响判断的说**。残留文件、文件名不一致、已停用这类整理项合成一句。「正常」一句带过。
5. **看不出有没有按时跑的**：「说明与盲区」里点名了没配输出日志的定时任务，告诉常浩「这几个看不出有没有按时跑」。
6. **最后列「需要你定」**。只列要常浩拍板的，比如「这个任务还要吗」「是故意暂停的吗」，给出建议的处理顺序，问他处理哪几条。**不要自己动手。**
7. **常浩说「都处理」「你看着办」时**：
   - 只挪文件的整理项（残留文件、多余的同名配置文件、确认不要的任务）可以列成清单，一次确认。
   - 重启、手动触发、重新加载、改配置，仍然一条一条确认。
8. **补登记任务用途**。报告里没有「做什么 / 坏了影响」的任务，可以顺手问常浩要不要补登记到 `config.json` 的 `tasks` 里。写入前给他看要加的内容。

回复模板：

```
结论：3 个自动化停了或失败了，另有 6 项配置问题。报告：<路径>
1｜飞书频道桥｜停了，在反复重启｜原因：项目缺少依赖 ws｜影响：飞书群里 @ 机器人没反应
3｜路觅周报推送｜周一没跑成｜原因：定时运行时找不到 lark-cli｜下次运行：11 月 9 日 09:00
4｜数字分身健康检查｜3 天没跑｜那几天电脑是关机状态，多半不用管（推断）
顺手整理：14、16（已停用的任务、残留文件）
看不出有没有按时跑：Codex 额度守护（没配日志）
需要你定：8「数字世界同步」的脚本已经没了，还要这个任务吗？
建议先处理 1、3。回编号就行；每条我先说做什么、怎么回退，你同意再动。
```

## 三、判档规则

每个任务可能有好几条问题，按最重的一条归档。同一档里排序是：
1. 常驻服务挂了
2. 上次运行失败
3. 该跑没跑
4. 没加载
5. 配置写错、僵尸任务
6. 整理类问题

同一类问题涉及 3 个以上任务（比如都没加载）时，合成一条。

| 档 | 情况 |
|---|---|
| 需要处理 | 常驻服务没在运行，或异常退出后正在等待重启 |
| | 常驻服务这次加载以来启动 ≥ 20 次（反复崩溃，或反复正常退出又被拉起）；上次是被要求退出（SIGTERM）的除外，归「注意」 |
| | 定时任务上次退出码不是 0（被 SIGTERM 中途停止的除外） |
| | 该跑没跑：输出日志最后更新以来按计划漏了 ≥ 3 次，并且停更 ≥ 24 小时 |
| | 常驻、定时或监视类任务：配置文件在、没停用，但 launchd 明确说找不到它（根本不会运行） |
| | 路径用了 `~` 开头（launchd 不展开 `~`）；Program 没写完整路径 |
| | 僵尸任务：要运行的程序、脚本、内联命令里 `cd` 的目录或要执行的文件已经不存在 |
| | 程序没有执行权限；工作目录或日志文件夹不存在（launchd 会启动失败） |
| | 配置文件坏了、有读不懂的值，或是断掉的软链接 |
| | 同一个任务名有多个配置文件（合成一条，并说明系统在用哪一个） |
| | hermes 定时任务上次失败、结果没送达，或过点 15 分钟还没跑（多半是网关没在运行） |
| | crontab 里某条要运行的文件不存在 |
| 注意 | 常驻服务在跑，但这次加载以来启动 ≥ 5 次，或之前异常退出过 |
| | 常驻服务启动 ≥ 5 次，但上次是被要求退出（SIGTERM）后重新拉起的，多半是发版或手动重启 |
| | 常驻服务此刻在重启间隙（上次正常退出、启动次数不多） |
| | 已停用但当前还加载着（下次登录或重启后就不会再启动） |
| | 该跑没跑：漏了至少 1 次，但没到「需要处理」的程度 |
| | 配了输出日志，但日志文件从没生成 |
| | 最近 24 小时的日志末尾有报错字样（退出码那一项已经报过的不重复报） |
| | 日志文件 ≥ 200 MB；日志文件读不了 |
| | 已停用但配置文件还在（已停用的任务，文件缺失也只算「注意」）；只在登录或手动触发时运行的任务没加载 |
| | 定时任务上次被 SIGTERM 中途停止 |
| | 配置文件属主不对、或别人可写（launchd 下次加载时会拒绝） |
| | 文件名像备份却仍以 `.plist` 结尾；文件名和任务名不一致 |
| | LaunchAgents 里有不以 `.plist` 结尾的残留文件（`.bak`、`.disabled` 等） |
| | hermes 定时任务已暂停；任务文件读不了 |
| 正常 | 以上都没有。没配输出日志的定时任务（包括只配了错误日志、或输出到 /dev/null 的）也算正常，但在「说明与盲区」里点名 |

「该跑没跑」怎么算：
- **每隔 N 秒（StartInterval）**：日志最后修改时间到「现在减 15 分钟」之间，能放下几个 N，就是漏了几次。
- **按日历（StartCalendarInterval）**：数日志最后修改之后、「现在减 15 分钟」之前，按计划应运行的时间点有几个。周日写 0 或 7 都认。
- **一天的时间点密集地排在一段窗口里的**（至少 3 个点、相邻不超过 60 分钟，一天里另有一段更长的空档。常见于「当天补跑窗口」，例如 GitHub 中心每天 09:00 起每 15 分钟一个点：当天做成后，后面的点直接退出、不写日志）：按窗口算，数有几个已经整段过去、却一行日志都没有的窗口。窗口可以跨午夜。今天的窗口还没结束时，只有之前已经有整段漏掉才把今天也算上；否则今天还在补跑，不算。
- **其他多次的**（早晚各一次、全天每小时或每 15 分钟一次）：每次都是独立的运行，仍逐次计数。
- **常驻服务**不按时间判断，看它在不在跑、重启了几次。配了日历计划的「异常时重启」类常驻服务，两样都看。

launchd 状态读不到时（在 SSH、沙箱或没有图形登录的环境里），不按「没加载」判档，只在「说明与盲区」里写明。只有 launchd 明确回复「找不到这个服务」才算没加载。

体检进程没权限看的路径（比如运行体检的终端没有「文稿」文件夹的授权），不当成「不存在」，只在「说明与盲区」里列出。

和上次对比时，「已恢复」只算这次也查过的范围：这次用 `--no-hermes`、`--no-crontab` 跳过的，被配置排除的，或这次没读到 launchd 状态的，都不算恢复。

退出码会翻译成人话：

| 退出码 | 意思 |
|---|---|
| 1 | 一般性错误，看日志 |
| 75 | 临时失败，常见于网络断开 |
| 78 | launchd 启动不了程序：路径不对、没有执行权限、`#!` 写错、日志或工作目录不存在 |
| 126 | 无法执行，常见于文件在「文稿」等文件夹里被隐私权限拦住 |
| 127 | 找不到命令 |
| 137 | 被强制结束 |
| 143 | 被要求退出 |

脚本能从日志里认出这些常见原因：
- 找不到命令
- 缺少依赖模块
- 被隐私权限拦住
- 没有权限
- 端口被占用
- 凭据过期
- 连不上对方服务
- 网络或域名解析失败
- 超时
- 磁盘满
- 内存不够
- 找不到文件
- 程序抛出的错误类型

## 四、只读边界

- 体检只运行两个程序、三种用法：`/bin/launchctl print gui/<UID>/<任务名>`、`/bin/launchctl print-disabled gui/<UID>`、`/usr/bin/crontab -l`。命令层按绝对路径和参数格式逐一核对，其他命令一律拒绝；测试里有一项运行时审计，盯住整个体检过程中的写文件和起进程。
- hermes 定时任务直接读 `~/.hermes/cron/jobs.json` 和 `~/.hermes/profiles/*/cron/jobs.json`，**不运行 hermes**：运行任何 hermes 命令都会触发它自己的启动维护（写日志、可能迁移配置、拉起被暂停的网关）。
- 脚本唯一会写的是报告的 `.md` 和 `.json`，两份里的家目录都写成 `~`。日志和命令里的密钥、token、密码、带密码的网址、机器人 webhook、私钥、手机号、邮箱都会被替换掉。
- 体检和回复的过程中，agent 只执行只读命令核实情况：上面的 `pmset -g log`、`last`，以及 `tail`、`launchctl print`、`plutil -lint`、`ls -l`。不加载、不卸载、不重启、不结束进程、不改文件、不挪文件。
- 处置是另一件事：常浩点名某一条后，读 [references/actions.md](references/actions.md)，一次一条，说清楚要做什么、会不会对外发东西、怎么回退，得到同意再做；做完重新体检，报告会显示「已恢复」。

## 五、配置

[config.json](config.json) 放在 skill 目录里，改完下次体检生效。agent 改它之前要先给常浩看改什么。写错的项（JSON 语法错、类型不对）这次按默认值体检，并在报告「说明与盲区」里指出来。

| 键 | 作用 |
|---|---|
| `tasks` | 按任务名登记：`名字`、`做什么`、`坏了影响`。报告里直接显示，agent 说影响时以它为准 |
| `aliases` | 任务名到中文名的通配对照（例如 `ai.hermes.*` → 飞书网关 Hermes），`tasks` 里没登记名字时用它 |
| `exclude_patterns` | 跳过哪些任务（系统和第三方厂商），支持 `*` 通配。跳过的会列在报告末尾，不会悄悄消失 |
| `include_labels` | 被上面排除、但其实是自建的任务，写完整任务名强制纳入 |
| `quiet_labels` | 平时就不写日志的定时任务，跳过「该跑没跑」判断 |
| `hermes_homes` | hermes 数据目录（默认 `~/.hermes`），会自动带上其中的各个 profile |
| `excerpt_lines`、`scan_lines` | 附录里每段日志摘几行（默认 6），读日志末尾几行来找报错和原因（默认 40） |
| `grace_minutes` | 判断该跑没跑时，给刚到点的任务留的余量（默认 15 分钟） |
| `missed_runs_act`、`stale_hours_act` | 漏几次且停更几小时算「需要处理」（默认 3 次、24 小时） |
| `restart_runs_warn`、`restart_runs_act` | 常驻服务启动几次算「注意」「需要处理」（默认 5、20） |
| `log_size_warn_mb` | 日志多大算「注意」（默认 200） |
| `recent_error_hours` | 多久以内的日志报错算数（默认 24 小时） |
| `hermes_overdue_minutes` | hermes 任务过点多久没跑算「需要处理」（默认 15，和 hermes 自己的判断一致） |

## 六、局限

- **「该跑没跑」是推断**，依据是输出日志的修改时间，错误日志不参与，因为任务正常时通常不写它。下面几种情况都会让判断偏严，所以要先按第二节第 1 步核实：
  - 任务平时就不写日志：加进 `quiet_labels`。
  - 电脑那段时间睡眠或关机。
- **只看用户级**的 `~/Library/LaunchAgents`，不看需要管理员权限的 `/Library/LaunchDaemons`。
- **启动次数和退出方式只看得到一部分**：
  - `launchctl print` 里的启动次数，是这次加载以来的累计，登录、重启、重新加载后清零。
  - 只看得到最后一次是怎么结束的。上次是 SIGTERM 时，之前有没有崩溃过看不出来，所以只归「注意」。
- **有几条未在本机实测**：
  - 日历计划里 Day 和 Weekday 同时写时，按 cron 的「任一满足」处理。
  - 软链接形式的配置文件，登录时会不会被 launchd 跟随，没有找到可靠来源。
- **hermes 的 `jobs.json` 字段**按 hermes-agent 2026-11 的源码对齐。hermes 改格式后，可能有字段读不到；最外层结构认不出来时会报「注意：任务文件格式认不出来」，不会悄悄当成没有任务。
- **按窗口判断的任务发现得晚一些**：工作时段内每小时一次这类计划，也会被当成窗口按天判断，当天中途停掉要到第二天才报出来。
- **脱敏的两个取舍**：
  - 没有键名的 32–64 位十六进制串（有些 API key、webhook 签名是这种）不打码，因为它和 git 哈希分不开。
  - token 类键后面跟的是普通英文单词时不打码（例如 `invalid token: signature mismatch`），免得把报错原文藏掉。password、secret、api_key 这类键一律打码。
