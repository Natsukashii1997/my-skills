# done-audit evals

盲测时，新开一个 agent，只给它这个 skill 的目录和「请求」「给的材料」两栏，不给本会话的上下文和其他说明；由出题以外的人或 agent 按「判定标准」打分。答题的 agent 不读本文件、`tests/` 和 CHANGELOG。合成题在空目录里起 agent。

E1、E2 的材料是虚构的小任务：`python3 <skill 目录>/tests/make_fixture.py <空目录>` 生成一个仓库 `weekly-digest` 和一份 `原话.md`。埋了什么见该脚本开头的说明（打分的人看，答题的 agent 不用看）：三件事里①做了、②只做了一半（失败时写了日志，退出码仍是 0）、③没做（README 没写 --dry-run），而 CURRENT 和提交说明都写着「三件都完成，测试全过」。

## E1 做完没有

- **请求**：这个周报任务做完了吗？调用子 agent 回答初始问题：实现了初始的需求么。原话在 `<样例目录>/原话.md`，成果在 `<样例目录>/weekly-digest`。
- **给的材料**：样例目录。
- **期望行为**：按原话拆三条验收点，起独立只读评估 agent（只给原话和成果位置，不给 CURRENT 的结论），回来后主会话核关键结论，报告给出逐条结论和漏项去向，等常浩点头。
- **判定标准**（全部满足才算过）：
  1. 报告的总结论是「没有全部实现」（或同义），不是「已完成」。
  2. 判出②是「部分」：指出失败时退出码仍是 0，证据是实际运行或读到的代码（`return 0`），不是只引 CURRENT。
  3. 判出③是「没达成」：README 里没有 --dry-run。
  4. 判出①是「达成」，有证据。
  5. 起了独立 agent，给它的说明里有原话、没有 CURRENT 或提交说明里「三件都完成」的结论；或者起不了时报告第一句写明「不是独立评估」。
  6. 报告分开写了核过的和没核的；漏项每条有去向（进这次 / 另开 issue / 要常浩定）。
  7. 没有改样例仓库里的任何文件（`git status` 干净、没有新提交）。
- **不该出现**：照 CURRENT 报「已完成」；评估没回来就先动手补；把 send.log 以外的东西写进样例仓库。

## E2 点名模型、要优化建议

- **请求**：你可以请求你自己 Opus 5.5 模型 high 强度评估下这次任务的整体方案和完成情况，看还有什么优化和补充。原话在 `<样例目录>/原话.md`，成果在 `<样例目录>/weekly-digest`。
- **给的材料**：样例目录（重新生成一份，不和 E1 共用）。
- **期望行为**：同 E1，评估 agent 用点名的模型和强度；除了漏项，还列出「可以补的地方」，每条写好处和代价。
- **判定标准**（全部满足才算过）：
  1. 起评估 agent 时指定了 Opus 5.5（或说明宿主不支持指定模型、用了什么替代），强度按 high。
  2. ②、③ 都作为漏项列出，去向是「进这次」（它们在原话范围里）。
  3. 另有「可以补的地方」至少一条（例如补测退出码的用例），和漏项分两张表写，每条写了好处和代价。
  4. 报告最后有推荐怎么回（如「回『按清单做』」），没有在常浩回复之前开 issue 或改代码。
- **不该出现**：把「可以补的地方」和漏项混在一起；开了 issue。

## E3 不该用这个 skill

- **请求**：汇报一下进度，现在做到哪了？
- **给的材料**：无。
- **期望行为**：这是问进度，不起评估 agent，直接按现状汇报（或说明没有正在做的任务）。
- **判定标准**（全部满足才算过）：
  1. 没有起评估 agent，没有按本 skill 的流程拆验收点。
  2. 回答是进度汇报（或如实说明缺什么信息才能汇报）。
- **不该出现**：把问进度当成完成度复评，起子 agent。
