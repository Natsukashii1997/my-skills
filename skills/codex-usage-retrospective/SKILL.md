# Codex 使用与行动复盘

复盘对象是在 Codex 中有证据的工作行为及其结果。目标是改善判断、投入顺序、协作和合格交付，让纠正逐渐变成前置能力。不要用配置健康、使用时长、工具次数或 Skill 数量代替这个目标，也不要推测未记录的线下生活、人格或心理状态。

## 先确定本轮边界

- 一次性运行采用用户指定窗口；定时运行读取该自动化的节奏与时区。默认北京时间每月 1 日、16 日复盘刚结束的半个月，区间左闭右开：1 日对应上月 16 日至本月 1 日，16 日对应本月 1 日至 16 日。延迟执行按计划到期窗口补做，不能按实际醒来日期悄悄丢掉漏跑期。
- 把目标、时间窗口、来源范围、交付位置、当前授权和停止条件写入本期报告开头，已明确的内容不重复询问。用户临时提出不同窗口时，不重写已有定时任务。
- 默认涵盖本机可访问的 Codex 父聊天，包括归档中本期有实际活动的聊天；子代理作为父任务证据，不能重复计为独立用户行为。ChatGPT 云端聊天、其他设备、线下工作和团队成员行为只有当前明确纳入且可取证时才算覆盖。
- 读取上期报告与行动状态；没有上期报告就建立首期基线。历史结论只是待核验线索，当前用户纠正和原始证据优先。上期已修复问题本期检查是否复发，不默认仍然存在。
- 开始取证前读取 [证据与状态规则](references/evidence-and-state.md)。本轮只读诊断无需升级权限或安装新能力。

## 取证：先覆盖，再深挖

1. 用 Codex 的 `list_threads`、`list_archived_threads`、`read_thread` 确認可读范围。列表是发现入口，返回条数或最近 50 条不是全期分母。按需使用 `scripts/period_index.py --help` 获取本地父聊天候选；它只补清单，不能证明消息正文完整可读。读取预算或分页不完整必须进入覆盖限制。
2. 建立轻量证据清单：聊天 ID、原题名、实际事件日期、任务类型、相关消息/成果指针、可读程度、选入原因。正文优先用 `read_thread`，先在工具侧投影用户要求、关键纠正、最终输出和必要验收；不把原始工具参数、全部日志、完整会话反复带回上下文。
3. 在可读清单中按不同任务类型、结果和重要性选择深读样本：有价值的成功、显著返工、重要决策、长链路未闭环，以及上期行动的验证机会。重要损失或权限异常应优先。样本数量随实际工作量调整，不为凑案例额外读取无关私人内容。
4. 每个重要案例还原“起点认知/目标 → 行动 → 结果 → 纠正或取舍 → 当前状态”。证据优先级为当时用户原话、实际交付与回执、当前可核验状态，其次摘要。需要对比时读取必要的前后记录，不能只截取纠正句判断谁有错。
5. 分别说明清单覆盖与深读覆盖：已发现多少、实际可读多少、深读哪些、有哪些缺口、哪些结论受影响。无固定可验证分母不报错误率、整体完成率或全期效率。

只有读取异常或案例证据指向运行问题，才定点检查配置、日志、Skill 或环境。工具报错、长会话、上下文压缩只是诊断线索，不自动等于用户效率低或业务失败。

## 判断：分清原因、责任和变化

对真正影响结果的案例，分别检查以下三层；允许某一层没有问题：

| 层次 | 关注对象 | 不应替代的判断 |
|---|---|---|
| 用户决策与行动 | 目标是否真实、关键未知先后、优先级、共享资源、取舍、授权、验收与后续采用 | 不把所有问题归因于“提示词不够好”；不推测性格 |
| 助手执行 | 是否读懂交付类型、守住范围、查证前提、提出关键取舍、落实纠正、完成验证 | 用户已讲清楚的要求不再要求用户重复管理 |
| 系统与组织条件 | 数据/权限、依赖、工具限制、验收人时间、环境采用、责任交接 | 不把客观约束伪装成用户或助手努力不足 |

优先回答：本期最值得保留的做法是什么？哪些损耗反复出现、为什么？哪一两个改变最可能改善下一期结果？重要问题标注“致命 / 重要 / 建议”，按实际影响解释等级，不制造危机。

- 区分正常受众或偏好调整、需求真正变化、助手遗漏、探索性试错和可避免返工。正常协作不是失败。
- 问题状态用“新发生且未解决 / 本期发生已修复 / 跨期跟踪已关闭 / 再次发生 / 风险假设 / 证据不足”。频次按唯一事件计，不按摘要、导出副本或重复引用计。
- 记录反例与成功恢复。已经修复并获得相应验收的交付不重做；不要额外索取与本轮交付无关的生产验收。
- 对因果先给可证伪解释及证据，再给关键未知和竞争解释。一次案例只支持局部判断；跨场景出现同一机制，才提高可复用置信度。没有行为前后证据，不称“已经成长”或“习惯改善”。
- 比较方法必须有同输入、同环境和同指标的当前基线。机器耗时、本地测试、用户验收、业务收益分开报告；缺少人工投入或质量数据，不声称提效。

## 优化：闭环少数重要改变

先验证上期行动：有效并保留、出现复发、尚未执行、没有适用机会、已暂停或无法验证。未承诺本期执行和明确暂停的项目不算逾期。不要机械追加越来越长的建议清单。

每项新改进写明：对应原因、谁负责、具体改变、首次适用场景、何种证据算有效、何时停止或调整。优先减少不必要投入、前置关键判断或修复真正阻塞；不默认增加审批、专家轮次、模板、模型、插件或自动化。

**执行权限与沉淀位置：**

- 本轮复盘报告、证据索引、行动状态和方法建议可在已指定的本地复盘输出目录生成并回读。这是复盘交付记录，不是新的正式知识库。
- 对其他工作文件的优化，只有当前请求或仍有效合同准确授权了对象、变更范围和完成标准，才直接实施；先保存必要备份、核对当前内容、做适度验证和写后回读。正在被其他任务修改的对象先保持只读，避免相互覆盖。
- 例行复盘默认不修改全局 `AGENTS.md`、已安装 Skill、自身 Skill、配置、权限、模型、定时计划或正在运行的项目。发现值得固化的改进，先提供可审核的具体候选；复盘请求本身不是永久自我修改授权。用户本轮明确要求修改某对象时按对应入口执行，不重复索取已有授权。
- “沉淀”首先体现在报告中形成可复用方法建议：适用问题、触发信号、输入与前提、关键判断、异常/失败信号、输出与验证、适用边界、证据成熟度。区分稳定机制、情境策略和单次经验；没有值得复用的发现时不硬凑。
- 写入 Obsidian 候选或 Codex 长期记忆、晋升正式知识、外发、部署、付费、安装或扩大权限遵守当前专门授权与合同。保存方法不等于自动推广为全局规则。当前没有保存授权时，报告中的建议就是完整交付，不把待批准写入伪称已完成。

## 交付并结束

正文用专业、中等篇幅中文，结论先行。默认一份报告及必要的最小状态，不拆成大量同义文档。内容应使用户无需读代码就能理解：

1. 本期关键判断、覆盖与证据限制。
2. 有效实践和关键问题，包含少量前后行为证据、原因与当前状态；没有重要问题可直接说明。
3. 上期改进核验、本期已完成的优化及验证、仍需用户决定的具体事项。
4. 下期少数可检验行动和可复用方法建议；给出精确来源及成果链接，不复制敏感原文。

写完回读报告与状态，核对日期、指针、去重、授权、已修复项、结论证据、未知范围及行动归属，再提交完成摘要。到期窗口有活动但资料不全时交付“部分覆盖复盘”，完成独立可支持的部分；不能冒称全量。确证无活动时只保留简短记录，不制造优化或催办。

停止条件：关键发现均有可追溯依据；优先改进与原因、行动和验证连通；已有授权的必要动作已完成并回读；缺口和待决事项明确。无新增证据时不反复扫描、不无限优化。真实运行后的效果仍以之后的行为变化、合格交付和用户反馈检验，结构校验与合成测试不能替代它。

## 设置定时任务时

仅在用户要求创建或修改定时复盘时处理计划。先查已有相同任务，优先更新而非重复创建；通过 Codex `automation_update` 设置当前聊天的 heartbeat，保留模型与推理设置。不要手改自动化文件或擅自建独立聊天。

将本 Skill 的绝对路径、节奏/时区、固定输出目录、首期窗口、覆盖边界、允许动作和通知条件写进人类可读的计划提示词。创建后回读真实计划及下次运行时间；工具不支持所需节奏时如实说明，不偷换为其他计划类型。定时成功登记不等于首次真实复盘已运行；说明本机需开机且 Codex 桌面应用运行。
