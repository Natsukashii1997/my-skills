# 提案.md 的格式

写在输出目录下，和 `sessions.md` 放在一起。整份文件只给常浩本人看，不外发。

## 骨架

下面的会话编号、次数、skill 名、项目都是虚构的示例，只用来看格式，不要照抄内容。

```markdown
# skill 进化提案：2026-09-07 至 2026-09-13

- 覆盖：有真人发话的会话 42 个（Claude 35、Codex 7），项目 proj-alpha、proj-beta 等 6 个
- 缺口：codex_zst_unread=3（Codex 有 3 份已压缩的记录没读到，Codex 上的活可能没看全）；没取到 issues.json（没网），候选池没对照
- 结论：新候选 2 条、改进 1 条；最值得做的是 N1

## 一、最值得做的

1. **N1 访谈纪要入库**：同一套做法这周做了 3 遍，每遍都从头讲，其中 1 遍把「待确认」的结论也写进了表。
2. **E1 doc-polish**：两次用完都被追问同一句「原文别动」。

## 二、新 skill 候选

### N1 访谈纪要入库（暂定名 interview-intake）

- **做什么**：常浩说「把这场访谈整理进表」时，读会议妙记，提炼痛点、原话、结论三类内容，写进访谈记录表。输入：妙记链接、目标表；判断点：哪些是受访人原话、哪些是主持人复述，结论里「待确认」的不入库；输出：表里新增的记录和一段摘要。
- **依据**：H04、H11、H19 三次走法一致（读妙记 → 分三类 → 写表）；H19 里被纠正「待确认的不要写进表，上次说过」（行 212）。
- **成熟度**：可立项
- **为什么是 skill**：步骤固定，但哪句算原话、哪条结论够不够确定，每次都要读上下文判断，脚本做不了；由常浩发起，不是到点就做的事。
- **和现有 skill 的分工**：lark-minutes 只管读妙记，lark-base 只管写表；这个候选管中间「怎么分类、什么不入库」。
- **怎么做**：开立项 issue 写边界 → 把三次会话里一致的步骤写成 SKILL.md，三类内容各放一个例子 → 拿 H04、H11、H19 的起始请求当 evals，另加一条不该用的 → 审计、盲测、PR。约半天。
- **推荐**：做

### N2 竞品周扫（暂定名 rival-scan）

- **做什么**：……
- **依据**：H27 一次。
- **成熟度**：继续观察（只出现 1 次，下周再有同类会话就够立项）
- **为什么是 skill**：……
- **和现有 skill 的分工**：……
- **怎么做**：先开候选 issue 记一笔，不动手写。
- **推荐**：观察

## 三、现有 skill 改进

### E1 doc-polish：每次都要补同一句

- **skill**：doc-polish（自建，1.2.0）
- **问题**：每次都要补同一句
- **依据**：H08（调用在行 31）之后常浩补了「原文别动，新建副本改」（行 40）；H22（调用在行 15）之后又补了同一句（行 26）。
- **改法**：第 1 步原句「读取文档后直接修改」→「读取文档后先新建副本，只改副本；常浩说『直接改原文』时才改原文」。
- **推荐**：做

## 四、上次的提案现在怎样

- N2（2026-08-31 周，继续观察，候选 #131）：这周又出现 1 次（H27），累计 2 次；走法还不一致，仍是继续观察。
- E3（2026-08-31 周，常浩批了「做」）：PR #88 还开着，没合并。

## 五、转交（不适合做成 skill 的）

- 「合并前先跑全量测试」被纠正 2 次（H14、H17）：是规则，建议跑一次 session-retro。
- 每天早上手动查一遍服务状态（H30、H31、H33）：每步都确定，该做成定时任务，不是 skill。

## 六、筛掉的

看过但没提的 5 组：一次性的小事 3 组；已有 skill 覆盖而且用上了的 2 组。

---
怎么批：回复「做 N1、E1」「N2 继续观察」「都不要」。
```

## 写法要求

- **六个节**的标题和顺序不变，空的节写「无」。`check` 会查。
- **缺口**：`sessions.json` 里报的每个缺口（如 `codex_zst_unread`、`files_unreadable`）都要用原名写在开头的「缺口」一行，并说它意味着什么没看全。没取到的材料、因此没做的判断也写在这一行。`check` 会查原名在不在。
- **编号**：新候选 `N1`、`N2`……，改进 `E1`、`E2`……，标题用三级标题 `### N1 名字`。两类加起来不超过 7 条。
- **必填项**，每项一行，写成 `- **名字**：内容`，`check` 会查：
  - N 类：做什么、依据、成熟度、为什么是 skill、和现有 skill 的分工、怎么做、推荐
  - E 类：skill、问题、依据、改法、推荐
- **依据**里必须有 `sessions.md` 里的会话编号（`H01` 这种），让常浩能回到出处。引用原话用清单里已脱敏的片段，加行号。只看了清单片段、没用 `context` 看前后文的，写明。跨周累计的写候选 issue 号（`#123`）。`retro/signals.md` 里的 `S1`、`S2` 是另一套编号，不能当依据。
- **成熟度**以「可立项」或「继续观察」开头。「可立项」要有 2 个以上会话编号，或 1 个会话编号加 1 个候选 issue 号。
- **推荐**只以「做」「观察」「不做」之一开头，后面可以跟一句理由。成熟度「可立项」配「做」或「不做」，「继续观察」配「观察」或「不做」。
- **做什么**要写出输入、步骤、判断点、输出，让没看过会话的人知道这个 skill 会干什么。
- **怎么做**写到能直接开工：下一步是什么、拿哪几个会话当 evals、大概多大的活。
- **改法**尽量给原句和改后的句子；改动大的写清改哪一节、加什么。
- 没有任何值得提的：一、二、三节都写「无」，结论写「本周没有值得做的」。
