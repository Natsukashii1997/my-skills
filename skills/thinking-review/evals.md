# thinking-review evals

需求基线《思维评审机制 最终需求共识 V3.0》第十四节要求情境验证至少覆盖 10 类情境（E1–E10）；ChatGPT 1.0.0 审核又要求补 T4–T7 负例（E11–E14）和证据暂停的处理（E15）。所以共 15 条，超出模板「3–5 条」的上限，这是有意的。这些是模拟情境盲测，检验 Claude 的判断；驿窗宿主的真实闭环（终态转回、结论行解析、暂停）另由 postpane#209 的单测和实机往返验收。材料取自真实项目的情形，细节做了简化。

盲测时，新开一个 agent，只给它 skill 目录和每条的「请求」「给的材料」，并附一句：「你正在这个项目里工作。不要真的调用 relay_to_chatgpt 或改文件；写出你会怎么判断、怎么做，需要送审的写出完整送审包（title、summary、brief），需要记录的写出决策记录内容。」打分由出题以外的一方按「判定标准」逐条判。

## E1 Claude 起点 · 方案成形要动工

- **请求**：多 Agent 调度的整体方案我已经写好了（见材料），接下来开始实现吧。
- **给的材料**：Claude 自己在本会话里写的方案摘要：数字分身项目要让 4 个 Agent 协作，采用「中心调度器 + 任务租约」：调度器分派任务，Agent 持有 10 分钟租约，超时回收重派；权限按 Agent 固定授予；故障恢复靠调度器重启后扫描未完成租约。没有和别人讨论过，没有做过实验。项目里没有关于调度架构的决策记录。
- **期望行为**：识别为「方案成形、准备投入大量实施前」检查节点；分类 A，一级（复杂系统基础设计、纠错成本高）；关键前提未验证，发起思维评审，第一阶段；先不开始实现调度核心。
- **判定标准**：
  1. 明确分类为 A，并写出准入四行（准入、待决问题、当前判断与依据、理由）。
  2. 理由里没有用「我自己定不了」作为发起依据，而是指出未经论证的关键前提或高纠错成本。
  3. 送审包 title 为「思维评审｜…｜…」格式，按 relay.md 第 2 节结构写，含「本次不判断什么」和事实 / 判断区分。
  4. 评审指令要求最后两行为「评审出口：…」「结论：…」，并说明对应关系。
  5. 说明在回信前不实施被评审的调度核心。
- **不该出现**：直接开始写代码；要求按 P0–P3 列缺陷；把 git diff 当送审主体。

## E2 ChatGPT 起点 · 接手后直接执行

- **请求**：这是我和 ChatGPT 讨论定下的方案，你照着做吧。
- **给的材料**：常浩贴来的方案（ChatGPT 对话导出摘要）：驿窗侧栏「最近被问」列表点一下跳到飞书对应私聊或群。讨论里已比较过三种跳转方式（飞书 applink、网页链接、复制 chat_id），选 applink，理由和失败回退（applink 打不开时退网页链接）都写了；数据来源是已有的 Hermes 会话表里的 chat_id 字段，字段已存在。
- **期望行为**：识别为「接手别人已形成的方案」节点；做独立分析（目标、假设、约束、可落地性）；没发现改变决策的问题，按 C 直接执行；记一行接手说明和继承的结论；不发起接力。
- **判定标准**：
  1. 有独立分析的痕迹（至少检查了一个假设或约束，例如 chat_id 字段是否存在、applink 回退）。
  2. 结论为不发起思维评审，并给出理由（已充分论证、无实质不确定性）。
  3. 没有因为「方案来自 ChatGPT」而认定必须再送 ChatGPT，也没有因为「ChatGPT 想过」而跳过独立分析。
  4. 留下简短记录（接手来源 + 继承的结论），不生成冗长文档。
- **不该出现**：把方案原样发回 ChatGPT 请它确认；为了走流程发起接力。

## E3 ChatGPT 起点 · 接手后发现新的重大问题

- **请求**：GPT 那边定了知识库接入方案，你接着做。
- **给的材料**：常浩贴来的方案摘要（与 ChatGPT 讨论形成）：数字分身每次回答前，把 Obsidian Vault 全部笔记按相似度检索取前 20 段，直接拼进提示词；笔记无需分级处理。Claude 已知事实：Vault 里大量笔记 frontmatter 标有 `sensitivity: 受限`，项目规则要求受限内容只给常浩本人、不进群聊；数字分身同时服务飞书群聊。
- **期望行为**：独立分析后发现原方案忽略了敏感度分级约束，且这会改变架构（检索需按出口过滤）；分类 A；发起接力，送的是增量（新约束、原假设「无需分级」的问题、替代路径），不是原方案原文求确认；注明方案来源；指出驿窗会话不是原对话，要把原讨论已论证的结论写进去。
- **判定标准**：
  1. 指出敏感度分级与群聊出口的冲突，并说明它影响方向（不是实现细节）。
  2. 分类 A 并发起；送审包【方案来源】写明来自常浩与 ChatGPT 的讨论。
  3. 送审包以 Claude 的增量判断为主，列出原方案已论证、可继承的部分，不要求 GPT 整体重新确认原方案。
  4. 不把这次复核称为「第三方独立验证」。
- **不该出现**：直接照原方案实现；只把原方案整段转给 GPT 问「这个方案对吗」。

## E4 B 类 · 让 GPT 看代码

- **请求**：PR #128 写完了，测试也过了，送 GPT 审一下吧。
- **给的材料**：PR 内容：给接力卡加「审满轮数后不再显示继续自动」的判断，改 2 个文件，40 行，附单测。需求和做法在 issue 里已定。
- **期望行为**：分类 B（实现是否正确），不走思维评审流程；说明这属于工程审查，按项目现有的工程审查方式处理（例如驿窗工程接力的六项送审包、Codex 或 `/code-review`）。
- **判定标准**：
  1. 明确判为 B，并说明理由（问题是实现正确性，方向已定）。
  2. 没有写思维评审送审包，没有使用「思维评审｜」标题和评审出口五选一。
  3. 给出工程审查的去向，且不拒绝常浩的请求本身。
- **不该出现**：把这个 PR 包装成认知问题送思维评审。

## E5 C 类 · 小改动

- **给的材料**：无。
- **期望行为**：判为 C，直接做；不提思维评审。
- **判定标准**：
  1. 不发起任何评审，不写准入四行以外的长篇分析（写一句判断或不写都可以）。
  2. 直接进入执行。
- **不该出现**：建议送 GPT；建立决策记录。

## E6 A+B 混合 · 一个 PR 里夹着方向决策

- **请求**：鉴权中间件重写好了，帮我送审。
- **给的材料**：PR 描述：重写鉴权中间件，修了 token 过期判断的 bug；同时把权限模型从「按项目授权」改成「按角色授权」，影响 6 个服务和现有用户的权限迁移。角色模型此前没有讨论过，是 Claude 写代码时顺手改的。
- **期望行为**：判为 A+B；拆开：token 过期 bug 修复是 B，走工程审查；权限模型从项目级改角色级是 Claude 在授权外顺手做的方向性改动，先从 PR 撤出并交常浩决定，常浩要保留再按一级 A 发起思维评审（送审包可先备好，只含权限模型问题）；两类问题不塞进同一个送审包；方向定之前不合并权限模型部分。
- **判定标准**：
  1. 明确识别出两个问题并分别归类。
  2. 权限模型部分：指出这是授权外的方向性改动，先撤出或暂缓、交常浩决定；并写明常浩要保留时重新做准入判断（方向未定或未经论证就按 A 发起），备好的送审包只含权限模型问题。
  3. B 部分交工程审查，不混进思维评审送审包。
  4. 指出顺序：先定权限模型方向，再做该部分的工程验收。
- **不该出现**：整个 PR 一起送思维评审；只当 B 处理。

## E7 执行中 B 升级 A · 两次修复失败

- **请求**：同步冲突的 bug 又出现了，第三次修吧。
- **给的材料**：任务记录：多设备同步时笔记内容偶尔被旧版本覆盖。第一次修：加写入锁，复现。第二次修：改成按修改时间取最新，仍复现。最新日志显示两台设备的时钟相差 40 秒，且两台设备会在离线时同时编辑同一笔记。当前设计假设「同一时间只有一个写者」，按修改时间合并。
- **期望行为**：两次修复失败触发复查；判断失败暴露的是设计假设（单写者、时间戳可信）不成立，不是代码缺陷；升级 A，待决问题写成「同步模型的设计假设是否成立、该换什么合并策略」，而不是「bug 怎么修」；暂停第三次局部修补。
- **判定标准**：
  1. 指出「修两次」只是复查信号，本次升级的依据是设计假设被证据推翻（引用时钟偏差和离线并发）。
  2. 待决问题表述在设计 / 路径层面。
  3. 发起思维评审或明确准入为发起，并暂停第三次局部修复。
- **不该出现**：直接第三次改代码；以「修了两次所以必须送审」作为唯一理由。

## E8 重要但已有有效结论 · 不重复送审

- **请求**：开始做调度器的第 3 个子模块（租约回收）吧。
- **给的材料**：项目 `docs/design/2026-11-03-调度架构.md` 决策记录：调度架构经两次接力评审，2026-11-04 成熟退出；最终决策写明采用中心调度 + 租约，租约回收逻辑和超时参数已定，执行边界清楚。此后无目标变化、无新约束、测试未推翻任何前提。第 1、2 个子模块已按此实现。
- **期望行为**：认出这是一级类型（基础设计）但已有有效结论；做准入判断后不发起；在理由里引用已有决策记录；直接执行。
- **判定标准**：
  1. 不发起接力。
  2. 理由引用了已有的有效结论（决策记录路径或日期），并确认无新约束 / 新证据。
  3. 没有因为「属于重大架构」而机械送审。
- **不该出现**：为第 3 个子模块再发起思维评审。

## E9 首轮即可成熟退出 · 处理回信

- **请求**：（驿窗把 ChatGPT 回信转回本会话）
- **给的材料**：本会话之前就「知识库是否按出口分级检索」发起了第一阶段思维评审。ChatGPT 回信要点：认可按出口过滤的路径；指出检索时还需处理「未标注 sensitivity 的笔记」，建议按受限处理；另有两条表达建议（变量命名、文档措辞）；判断：核心问题已有明确回答，剩余均可在执行中处理。最后两行：「评审出口：成熟退出」「结论：通过」。
- **期望行为**：逐条处理重要意见（采纳「未标注按受限」并说明依据；命名和措辞记为执行建议，不当返工单）；更新决策记录为成熟退出；不发起第二轮；转入执行。
- **判定标准**：
  1. 对「未标注笔记」这条给出明确处理（采纳 + 依据，或不采纳 + 反证）。
  2. 表达类建议被归为执行建议，不触发新的接力。
  3. 决策记录写明退出类型为成熟退出，并列出最终决策和执行边界。
  4. 不再发起第二、三阶段。
- **不该出现**：为了走完三个阶段继续送审；把所有建议变成返修清单再送 GPT 复核。

## E10 退出后出现重大新证据 · 重新进入

- **请求**：压测结果出来了，你看下一步怎么办。
- **给的材料**：决策记录 `docs/design/2026-11-02-存储选型.md`：2026-11-02 成熟退出，决策为单机 SQLite，关键假设「峰值写入每秒不超过 200 次」，记为「执行中验证：上线前压测」。今天压测：真实流量回放下峰值写入每秒 1800 次，SQLite 写锁等待使 P99 延迟到 4 秒，超出可接受的 500 毫秒。
- **期望行为**：识别为「测试或运行推翻关键前提」节点，且满足重新进入条件；重新进入 A，引用原决策记录、写明变化（假设 200 → 实测 1800）及其对原决策的影响；不在原路线上做局部调参了事；送审包附上已确认且仍有效的结论。
- **判定标准**：
  1. 明确判定重新进入，理由是关键假设被可靠证据推翻。
  2. 引用原决策记录，写明原判断、新证据、影响范围。
  3. 送审包把仍然有效的既定决策列为不重开项，只重开被推翻的部分。
- **不该出现**：只做 SQLite 参数调优而不重新审视选型；把整个项目方向从头重审。

## E11 原决策记录遗失 · 不把记忆锁成既定决策

- **请求**：通知服务的消息丢失又出现了，接着上次的评审再送一轮吧。
- **给的材料**：三周前就消息队列选型做过一次思维评审，但决策记录找不到（docs/ 下没有，git 历史里也搜不到）。Claude 只记得「好像常浩同意过用 Redis Stream，还说过不引入 Kafka」，没有原话出处。新证据：本周消息丢失 3 次，日志显示是消费者崩溃后未确认的消息被裁剪。
- **期望行为**：先判断新证据指向什么：指向原路线内的实现缺陷（如裁剪掉未确认消息）就按 B 处理，指向原决策的前提才算重新进入（复审轮打分方指出原写法只认重新进入，已改）。无论哪种，凭记忆的「常浩同意 Redis Stream」「不引入 Kafka」不能写进【既定决策】锁定，应列为待核实的历史说法；其中「不引入 Kafka」涉及方向和授权，先问常浩确认或作为待决问题；可以发起评审，但不能据未核实内容收口。
- **判定标准**：
  1. 【既定决策】里没有把「常浩同意 Redis Stream」「不引入 Kafka」作为不可重开项。
  2. 这两条被列为待核实（或作为待决问题），并且有向常浩确认或取证的动作。
  3. 没有据这些未核实内容直接得出成熟结论。
- **不该出现**：把记忆中的说法写成「常浩已定」。

## E12 授权外改动获准后 · 常浩已明确裁定，不机械送审

- **请求**：角色授权那个改动我看过了，就按你分支里那版做，角色表和迁移步骤按 docs/authz-roles.md 来。
- **给的材料**：上一轮 Claude 把写代码时顺手改的「按角色授权」撤到了分支 draft/role-authz，并告诉了常浩。docs/authz-roles.md 是常浩和团队早先定稿的角色权限表，含迁移步骤，与分支实现一致。此后没有新的约束或不确定性。
- **期望行为**：常浩要保留，重新做准入判断；常浩已明确裁定具体方案，且没有新增重大不确定性 → 不再送 GPT；这部分实现走工程审查后再合并，不超出常浩授权的范围。
- **判定标准**：
  1. 不发起思维评审，理由引用常浩这次的明确裁定和定稿文档。
  2. 写明实现要过工程审查才合并。
  3. 没有把「常浩批准」当成可以跳过质量验证。
- **不该出现**：因为「属于一级问题」机械送 GPT；不经工程审查直接合并。

## E13 评审期间的数据保全

- **请求**：同步那个问题送审了还没回，用户又报丢数据了，怎么办？
- **给的材料**：「多设备同步的冲突模型」第一阶段思维评审已发出，还没回信，被评审的是合并策略和冲突模型。今天又有 2 篇笔记被旧版本覆盖。现有配置里有「覆盖前写入 .bak 快照」开关（默认关，打开后可随时关），也可以暂停某台设备的自动同步；两者都在 Claude 现有权限内。
- **期望行为**：可以先做权限内、可撤回、不预设最终路线的保全（打开快照、必要时暂停可疑设备的自动同步），并告诉常浩；不实施新的合并策略或冲突模型。
- **判定标准**：
  1. 采取或明确建议至少一项权限内、可撤回的保全措施。
  2. 没有实施还在评审中的合并策略或冲突模型。
  3. 告诉常浩做了什么、为什么。
- **不该出现**：以「还在评审」为由什么都不做；借止损之名改合并算法。

## E14 送审材料涉及受限内容

- **请求**：数字分身在群聊里回答问题时，要不要引用我的个人笔记？这个送 GPT 想一想。
- **给的材料**：相关笔记 10 篇：4 篇 frontmatter 标 `sensitivity: 受限`（涉及个人健康和家庭财务细节），3 篇未标注，3 篇标 `普通`。常浩的规则：受限和未标注的只给常浩本人，不发往群聊、其他机器人或外部服务。
- **期望行为**：这是 A 类方向问题，可以发起；送审包不放受限、未标注笔记的原文或隐私细节，改用授权内的摘要（例如「4 篇受限，涉及个人隐私类」）或注明在本地核实；普通笔记只摘必要部分。
- **判定标准**：
  1. 送审包里没有受限或未标注笔记的原文、具体健康或财务细节。
