# 思维评审

这个 skill 让 Claude 在关键节点调用第二个独立的思考系统（ChatGPT High，经驿窗接力），提高方向、路径和重大决策的质量；一旦想清楚，就退出，让 Claude 自主执行。

它不是审批制度：不要求每件事过 GPT，不要求跑固定轮数，GPT 也不靠挑出问题来证明价值。评价它的标准只有一个：重大方向有没有走错，往返有没有变少。

三个角色：Claude 推进和执行，并负责判断要不要接力；ChatGPT High 做独立分析和认知校准；常浩定目标、拍板重大取舍，随时可以发起、否决或覆盖 Claude 的判断。

## 1. 什么时候做判断（检查节点）

在下面这些节点做一次分类判断。判断是持续的能力，但**持续判断不等于持续送审**：大多数节点判完的结果都是「不送，直接做」。

| 节点 | 要问自己的 |
|---|---|
| 接到任务，或接手别人已形成的方案（ChatGPT、常浩、其他 AI 给的文档、PDF、口述） | 这里还有没被有效论证、又会影响方向的判断吗？ |
| 方案成形，准备投入大量实施前 | 有没有一旦错了就要大范围返工的决定还没论证？ |
| 测试或实际运行推翻了某个关键前提 | 这个前提支撑着哪些决定？核心路径变了吗？（必须重判） |
| 同一问题两次修复失败 | 失败暴露的是代码缺陷，还是根因判断或设计假设错了？（只是提醒复查，不自动升 A） |
| 工程上反复返工，却总贴不上常浩的实际用法 | 是不是路线本身和真实使用方式不匹配？ |
| 常浩对方向提出质疑（例如「这还是 X 吗」「这个方向对吗」） | 质疑指向的是目标、前提还是路径？ |
| 评审结束后，出现目标变化、关键约束变化、原路线被证伪或重大系统冲突 | 是否满足重新进入的条件（见 references/exit.md 第 5 节） |

**不是**检查节点：每个 PR、每次提交、每个小功能、已定方案下的普通步骤。

## 2. 分类：当前要解决的是什么问题

按**当前这一刻要解决的问题**分类，不按项目类型、交付物形式、有没有代码、方案最初是谁想的来分。详细判据和误判例子见 [references/classify.md](references/classify.md)。

| 类 | 当前要解决的 | 去向 |
|---|---|---|
| A 思维与决策评审 | 方向对不对：问题定义、目标、根因、路径或方案选择、架构、方法论、关键前提 | 走第 3 节准入判断 |
| B 工程与质量审查 | 实现对不对：代码、测试、缺陷、回归、异常处理、验收证据 | 不走本 skill；交工程审查（Codex、`/code-review`、驿窗工程接力等）或自己测 |
| A+B 混合 | 两者都有 | 拆开：先把会改变方向的 A 问题论证完，再做 B |
| C 常规自主执行 | 目标和路径都清楚，风险由现有流程管得住 | 直接做，不额外评审 |

## 3. 准入：A 类候选要不要真的发起接力

先看五个方面（不打分，判断即可）：决策重要性（影响多大的后续工作）、不确定性（目标清不清、前提有没有验证、有没有实质取舍；**Claude 自己很有把握不算确定**）、系统关联性（牵涉几个模块、角色、流程）、纠错成本（错了要不要大返工、迁移数据、重构流程）、独立认知的预期增量（GPT 重构问题、比较方案、质疑前提，能不能真的改变方向）。

三级处理：

- **一级：必须做准入判断，有未论证的关键判断就发起。** 重大架构路线、核心目标变化、复杂系统的基础设计、重要业务方法论、跨模块的重大决策。这一级看的是问题本身的类型，不看 Claude 把握多大。但**同一问题已有有效结论、原决策仍成立、也没有新约束或新证据**时，不重复发起：一个大架构项目的每个子任务不需要逐个送审。
- **以下情况，A 类也可以不发起，在理由里写明即可**：常浩已经当场对这些判断拍板；分歧是目标层面的偏差，常浩的原话就能裁定；方案分批推进、每批可回退，错了代价小。常浩的明确判断和原话是最高优先级的证据，GPT 的论证不能替代它。
- **二级：按认知收益判断。** 方案取舍、局部设计冲突、中等规模的流程调整，已有相对明确的依据。值得就发起，不值得就做，两种都写一句理由。
- **三级：默认不发起。** 常规执行、局部开发、已定方案下的优化、一般 bug 修复和测试补充。

准入判断写成四行，放进决策记录（第 6 节），不另建文件、不填表：

```
准入：A｜发起 / 不发起
待决问题：<一句话，本次要判断什么>
当前判断与依据：<Claude 已经形成的看法；还没有看法就写「尚无」>
理由：<为什么值得独立论证；或为什么不必（已有有效结论 / 无实质不确定性 / 只是执行）>
```

「Claude 自己定不了」不是发起的必要条件。Claude 已经有答案、但关键前提不牢，正是最该送的时候。备选方案也不是硬门槛：还没有备选时，找出备选本身就是 GPT 的价值。

## 4. 接手别人已形成的方案（ChatGPT 起点）

方案先在常浩和 ChatGPT 之间形成，再交给 Claude，是常见情形。**思考来源不决定评审类型。** 不能因为 ChatGPT 想过就当它已经评审完，也不能因为方案来自 ChatGPT 就必须再送 ChatGPT。

Claude 接手后先做自己的独立分析，不只是复述或改写：原方案对目标理解准不准、关键假设可不可靠、有没有没考虑的约束、能不能落地、有没有更好的路径、哪些还要验证。然后：

- **没发现会改变决策的问题** → 按 C 直接执行。决策记录里写一行「接手 <来源> 方案，独立分析未发现改变决策的问题」，并列出继承的结论。
- **发现了新问题**（假设可能错、新约束、更好的替代路径、原结论和新证据冲突） → 走第 3 节准入。发起时送的是**增量**：Claude 的异议、新约束、新替代方案、怀疑的原始推理偏差。不要把原方案原样发回去请 GPT 确认自己。
- 驿窗接力开的是一个新的 ChatGPT 会话，看不到常浩原来那段对话：原方案里已论证的结论要写进送审包。新会话、同一模型，**不等于第三方独立验证**，回给常浩时不要这样称呼。

## 5. 发起接力与递进评审

用驿窗的 `relay_to_chatgpt` 工具发起。送审包怎么写、给 ChatGPT 的评审指令、回信结构、结论行怎么对接驿窗的自动往返，见 [references/relay.md](references/relay.md)：**发起前必读，结论行写错会被驿窗误判。**

评审按三个认知阶段递进。阶段是思考方式，**不是固定的三次接力**：一次回信可以走完全部三个阶段直接退出；缺事实时先暂停去取证，不靠多轮讨论模拟事实。各阶段要做什么、新问题凭什么能扩大范围，见 [references/stages.md](references/stages.md)。

| 阶段 | 回答的问题 | 范围 |
|---|---|---|
| 一 全景审视 | 问题提对了吗？目标、前提、路径、整体逻辑成立吗？ | 本次待决问题及必要的上下游，不是整个项目 |
| 二 关键深化 | 第一阶段留下的关键分歧，现在有充分依据了吗？ | 只处理决策记录里标为「需深化」的项 |
| 三 决策收敛 | 想清楚到足以行动了吗？剩下的由谁、在哪处理？ | 收口，不再做广泛探索 |

发出后，被评审的那个决定先不往下实施；与它无关的工作可以继续。回信会由驿窗转回本会话。评审进行中，常浩中途对某一项拍了板，就把它记为既定决策，但这不等于整个评审已经收口。只有评审退出，或者常浩明确说「开工」，才开始实施被评审的部分。

内容没有实质变化，不要重送。上一轮的意见没有处理完、也没有补上新证据，就再发一次，只会浪费一次高强度评审。

## 6. 收到回信：处理，不照单全收

对回信里每条重要意见给一个处理：采纳并说明依据；不采纳并给出反证；补证据后再判断；把分歧交常浩；记为执行阶段的优化建议。不是每条建议都要变成返工单，只改善表达、不影响判断的内容不消耗接力。

Claude 和 GPT 有分歧时，各自把证据摆出来交换一次。仍不一致且无法靠补充信息解决的，把两边的判断、证据和取舍交给常浩，不要循环到一方认同为止。

决策记录由 Claude 维护，一个认知问题一份，写在当前项目约定的设计文档目录里（如 `docs/design/`、`docs/adr/`；没有约定就用 `docs/thinking-review/`），不放 `/tmp`。模板见 [references/decision-record.md](references/decision-record.md)。记录的核心是「关键判断及其依据」，要能分清：原始方案是谁提的、哪些结论之前已论证、Claude 接手后新增了什么、每次评审解决了什么、最终决策是什么。它不是 GPT 意见的流水账。普通执行步骤和代码改动不进这份记录。

已确认的结论是后续工作的基线，没有新证据不重开；有新证据推翻时，记下原判断、新证据、影响范围和修正后的决策。

## 7. 退出

每个待决问题分开记两件事：**认知状态**（想清楚到什么程度）和**处理去向**（下一步谁负责、在哪做）。状态填上了，不等于问题解决了。四种退出及成熟条件见 [references/exit.md](references/exit.md)。

| 退出 | 含义 | 之后 |
|---|---|---|
| 成熟退出 | 核心问题已有明确判断，剩下的不确定性有受控的处理办法 | Claude 按已定路径自主执行 |
| 决策升级 | 分析已经清楚，剩下的是业务偏好、资源取舍、授权或风险接受 | 交常浩拍板；拍板前该决定不算成熟 |
| 证据不足暂停 | 再讨论也不会有新信息 | 先取证（测试、实验、数据、问人），有了再决定是否恢复 |
| 转其他路径 | 认知层面已经清楚，剩下的是工程实现、测试或普通执行 | 转 B 或 C |

退出不代表一切正确，更不代表可以上线，只代表这条思维评审链当前没有继续的必要。GPT 的认可不等于代码验收或上线授权。

退出后，后续开发不再因为每个小功能、每次代码改动回到这里。

## 8. 要防的失控

| 失控 | 表现 | 守法 |
|---|---|---|
| 审核泛化 | 什么都送 GPT | 先分类，B、C 不进来 |
| 重复触发 | 大项目每个子任务都送；同一问题换个名字再送 | 已有有效结论就继承，不重送 |
| 问题膨胀 | 每轮都冒出新的次要问题 | 后续阶段收缩范围；新问题过不了 stages.md 的四问就记为执行建议 |
| 深度错位 | 讨论方向时陷进代码细节 | 始终对准待决问题 |
| 共识反复 | 已确认的前提被反复质疑 | 决策记录是基线，没有新证据不推翻 |
| 退出失灵 | 只要还能优化就继续审 | 按成熟条件退出，不按完美程度 |
| 自我确认 | 把 GPT 的方案送回 GPT 求认可 | 接手后先独立分析，只送增量 |
| 过度收敛 | 为了快结束，压住真正的重大新问题，或把关键假设甩给执行阶段 | 新问题能改变核心决策就允许重开；关键假设错了会推翻架构的，不能「执行中验证」 |

## 9. 向常浩汇报

用一两句说清：这次判断了什么（分类和准入结果）、评审解决了什么、怎么退出的、接下来谁做什么。决策升级时，把选项、各自依据和 Claude 的推荐一起给出。不发起评审时不用专门汇报，决策记录里那几行就够了；常浩问起时能说清理由。
