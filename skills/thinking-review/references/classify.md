# 分类与准入：判据与常见误判

## 1. 一句话判据

先写下「当前这一刻真正要解决的是什么」，再看它是哪一种：

- 回答「**方向对不对**」：我们在解决正确的问题吗？目标合理吗？根因判断对吗？方案为什么成立？有没有更合适的路径？依赖的前提可靠吗？忽略了什么约束或长期成本？方案之间怎么取舍？新事实出现后原决策要不要改？→ **A 候选**
- 回答「**实现对不对**」：代码符合既定需求吗？有没有逻辑错误、bug、回归、安全漏洞？测试够不够？异常处理对吗？运行结果和测试证据可信吗？→ **B**
- 两者都有 → **A+B**，拆成两个问题分别处理。
- 两者都不是，目标和路径都清楚，只是要做 → **C**

同一个项目、同一个功能，甚至同一个问题的不同阶段，都可能分属 A 或 B。不能按项目名、有没有改代码、有没有 PR 来分。

## 2. 例子：一个 Agent 调度系统里的不同问题

| 当前问题 | 分类 |
|---|---|
| 要不要采用集中调度架构 | A |
| 多个 Agent 之间怎么划分权限和责任 | A |
| 某种调度机制能不能满足系统约束 | A，必要时需要实验支持 |
| 调度代码有没有正确实现已定机制 | B |
| 并发竞争、异常回滚、重复执行有没有漏洞 | B |
| 测试中发现原调度模型根本不适合业务，要重选架构 | 由 B 发现，升级为 A |

## 3. 两个方向的误判

**技术问题一律归 B（错）。** 技术架构、系统边界、长期维护策略、技术路线、关键授权原则，虽然发生在工程项目里，核心任务仍是选择和论证，属于 A。

**方案文档一律归 A（错）。** 一个已经明确的业务流程，只需要检查文档有没有漏掉既定条款、文字是否一致、是否符合已批准的要求，不存在值得独立思考的重要问题，是常规校对，属于 B 或 C。

不能用交付物的形式代替对问题性质的判断。

**A 定完路线后，落地核查还占着思维评审通道（错）。** 路线一旦定下，部署、交接、运行验收都属于 B。真实案例中出现过：路线定了以后，一天里又产出 5 份以上的「评审」文件，每一步都要等 ChatGPT。

**工程上反复返工，却一直当 B 修（错）。** 表面是工程问题，根子可能是路线和常浩的真实使用方式不匹配。升级为 A 时，拿常浩的实际使用方式当首要证据。

## 4. A+B 怎么拆

1. 把会改变方向的问题挑出来，单独写成待决问题。
2. 方向问题先论证，结论写进决策记录。
3. 实现质量问题按已定方向做工程审查。
4. 工程审查中又发现方向前提不成立时，回到 A（这是「由 B 升级 A」）。

不要把 A 问题和 B 问题塞进同一个送审包：GPT 会在两种思考方式之间来回切换，哪个都做不深。

## 5. 准入的五个方面（判断，不打分）

| 方面 | 问 | 越高越值得 |
|---|---|---|
| 决策重要性 | 这个判断影响多大的后续工作？（长期架构、大量开发投入、跨团队流程、重要业务策略、重大资源配置） | 影响越大 |
| 不确定性 | 目标清楚吗？重要假设验证过吗？多个方案有实质取舍吗？ | 越不确定。注意：Claude 已有明确答案但关键前提不牢，也算不确定 |
| 系统关联性 | 牵涉几个模块、Agent、角色、业务流程和信息流转？ | 关联越复杂，越容易局部合理、整体不合理 |
| 纠错成本 | 路径错了，修正要不要大范围返工、数据迁移、流程重构、重大投入？ | 越难逆转 |
| 独立认知增量 | GPT 重新定义问题、比较方案、质疑前提、找出遗漏，能对方向产生实质帮助吗？ | 增量为零时，再复杂也不必进入 |

## 6. 「必须判断」不等于「必须发起」

一级场景（重大架构路线、核心目标变化、复杂系统基础设计、重要业务方法论、跨模块重大决策）必须做准入判断，写下四行。是否真的发起，看两件事：

- 相关的重要认知问题有没有经过有效论证？
- 有没有出现实质性的新不确定性（新约束、新证据、前提被动摇）？

两者都是「否」（已充分论证、原决策仍有效、无新约束或新证据、只是执行已定路线）时，**不发起**，在理由里写明继承了哪份有效结论。

## 7. 「两次修不好」怎么判

连续两次修复失败，是提醒复查问题性质的信号，不是升级 A 的规则：

- 测试不稳定、一个明确的代码缺陷还没修对 → 仍是 B，换修法或请人看代码。
- 失败说明根因判断错了、设计假设不成立、解决路径本身有问题 → 考虑 A，待决问题写成「根因 / 设计假设 / 路径是否成立」，而不是「这个 bug 怎么修」。

## 8. 发起时的自检

- 待决问题是一个**认知问题或关键决策**，不是一份 PR、一次提交或一个功能点。
- 有没有针对同一问题的有效结论？有就继承，不重送；要重送就说明重新进入的原因（exit.md 第 5 节）。
- 没有把普通执行问题包装成认知问题。
- 没有把 B 问题混进来。
