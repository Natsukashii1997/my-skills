# 案例校准：哪些案例改了哪条规则

依据 cases.md 的 15 个真实案例（2026-11-07 整理）。cases.md 是仅存本地的受限材料（含本机会话与知识库摘要），不随打包分发、不外发。这里只记对规则产生影响的部分。

| 案例 | 暴露的问题 | 对规则的改动 |
|---|---|---|
| C-02 Obsidian 第二大脑 | A 类问题，但常浩当场拍板、方案分批可回退，没送审也没出问题 | SKILL.md 第 3 节：A 类在常浩已拍板、原话可裁定、可分批回退时可以不发起，理由写明 |
| C-05 回答收藏器 | ChatGPT 起点的 PRD 范围跑偏，用常浩原话一轮就纠正，不必回送 | 同上；常浩原话列为最高优先级证据 |
| C-04 Hermes 主动运营 | 评审进行中，常浩定了一项决定，Claude 当作开工信号抢跑 | SKILL.md 第 5 节：中途单项拍板记为既定决策，不等于收口；退出或常浩明说开工才实施 |
| C-08 DT-ORC V3.1.0 | 宣布「唯一长期共识」，几天后被实际使用证据推翻 | decision-record.md 增加「重开条件」 |
| C-10 AI 落地三步法 | 三轮评审都在看措辞，目标用户的前提问题由常浩发现；第 3 轮送的内容和上一轮一样 | stages.md 第一阶段先审目标用户与核心假设；relay.md 送审包增加【目标用户与核心假设】【常浩的原始诉求】；SKILL.md：内容没变不重送 |
| C-03 Obsidian K0/K1 | 路线定下后，部署和验收仍占着思维评审通道，一天里出了 6 份评审文件 | classify.md 增加误判「A 定完路线后落地核查还走思维评审」 |
| C-09 ORCA 改路线 | 工程上反复返工，根子是路线不合实际用法 | SKILL.md 检查节点表增加「反复返工却总贴不上实际用法」；classify.md 增加对应误判 |
| C-07 数字分身人设 | 常浩的质疑（「这还是 soul 么」）是该送审的信号 | SKILL.md 检查节点表增加「常浩对方向提出质疑」 |
| C-11、C-13 | 纯 B 类的续审轮数问题 | 不归本 skill；确认 SKILL.md 中 B 不走本流程 |
| C-14、C-15 | C 类正样本 | 确认 C 直接执行；不送审也不伪装成已审 |

## 仍缺的样本

- 类型 9（重要、已有有效结论、不该再送审）缺纯 A 的真实样本，目前用 evals E8 的构造情形补位。
- ChatGPT 侧材料缺口见 cases.md 末尾，不阻塞 1.0；补到后再复核 C-04、C-09、C-10。
